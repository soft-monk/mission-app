## 1. 判定标准（四条，权重大致递减）

| # | 判据 | 说明 |
|---|---|---|
| 1 | **会被本项目之外的消费者使用** | 独立版本号的唯一正当理由。没有第二个消费者，独立仓只增加发布摩擦 |
| 2 | **发布节奏与宿主不同** | 引擎改了要发版；宿主跟着业务改。节奏不同 = 该分 |
| 3 | **整目录拷到空工程能否独立构建、独立示例、独立测试** | 既有"交付验收九条"的第一条。做不到就是宿主身上的一块肉 |
| 4 | **公开接口能否不含消费者专有名词** | 出现 `T0–T7`、`光电无人机`、`A区`、`云边端`、`93%` 就是破线 → 该拆成"引擎 + 规则" |

> **反向判据**：把东西做成"可配置的通用模块"如果只会产出一堆
> `phaseRules.json` / `scoringWeights.yaml`，而**只有一个消费者**，那就别拆 —— 那是配置地狱。
> 只有判据 1 成立时，规则注入才有意义。

### 1.1 三种拆分动作

| 动作 | 适用 | 说明 |
|---|---|---|
| **直接建仓** | 全新的、或已经是独立目录的 | `geo-data`、`media-player`（后者已有雏形，需抽离） |
| **先拆再建仓** | 现在长在别的仓里的**单体文件**内 | `Api.cc` 里的六个引擎、`ai/rules.py` 里的规则、`map-2d/src/core/displayMode.ts` 里错放的组图映射 |
| **不拆** | 纯数据 / 纯定义 / 纯界面 | 见 §4 |

**每个引擎的三条硬约束（与 `DISC-04` 同级）**

1. 公开接口 MUST NOT 出现消费者专有名词（`T5`、`光电无人机`、`A区`、`云边端`、`93%`）
2. MUST NOT import 任何宿主；MUST NOT import 其它引擎内部（只走公开入口）
3. 必须能"只传配置 + 空数据"跑通一次（对齐 `map-2d` M2-MZ-02-01 的契约自足）

### 2.3 仓库形态：一个引擎一个仓，还是多包一仓？

| 方案 | 评价 |
|---|---|
| **A. 一个引擎一个仓**（10 个仓） | 版本独立最彻底，但 10 个仓的 CI / 变更单 / 依赖升级成本很高；且这些引擎**共享同一批领域概念**（实体、评分、阶段） |
| **B. 一个仓多包**（`mission-engine/packages/*`）✅ **推荐** | 共享类型定义与协议（对齐 `realtime-hub` 的"一个仓两个包"先例）；`changesets` 可逐包发版；发布节奏相近；**第二个消费者只要装一个仓就能拿到整套** |
| C. 全部塞进一个包 | ❌ 退化成单体库，判据 3（独立构建/测试）失效 |

**建议采用 B**：新建 `mission-engine` 仓，内部分 `packages/`（引擎）+ `policies/`（规则包）：

```
mission-engine/                     ← 新仓（可复用）
├─ packages/
│   ├─ phase-engine/                ├─ resource-alloc/
│   ├─ scoring/                     ├─ entity-ledger/
│   ├─ topology/                    ├─ view-composer/
│   ├─ alert-engine/                ├─ report-engine/
│   └─ selfcheck/
├─ policies/
│   ├─ mapapp/                      ← 本项目的 T0–T7、四型无人机、评分权重、区域命名
│   └─ <consumer-b>/                ← 第二个系统的规则（与上面完全隔离）
└─ protocol.md                      ← 与 realtime-hub 同款：包间唯一的约定
```

> `llm-provider` 建议**单独一仓**：它的消费者完全不同（任何要接 LLM/语音的项目），
> 且它已有现成雏形 `mapApp/ai/bridge.py`。

## 4. 不能拆分 / 不建仓的（留宿主仓）

| 项 | 为什么不建仓 | 现在在哪 | 将来在哪 |
|---|---|---|---|
| `mission-baseline` 场景基线 | **纯数据，没有生命周期**——本质是一套配置。给它建仓等于给配置建仓 | `backend/src/core/Seed.cc`（23.6 KB）+ `useStore.ts` 初始值 | 宿主仓（或 `policies/mapapp` 的数据部分） |
| 业务实体定义（任务/目标/方案/告警/报告的表结构） | 与 `biz-store` 的**存储机制**不同：机制可复用（可建仓），**实体定义只有一个消费者** | `backend/src` + `api/types.ts` | 宿主仓 |
| **T0–T7 的具体规则** | 属"规则"侧，与引擎分离；且第二个指挥系统的阶段定义不同 | `Api.cc` `phaseTitle` L66 + `useStore.ts` `PHASE_ORDER`/`PHASE_TITLES` L118–133 | `policies/mapapp` |
| **界面壳**（顶栏/左导航/底部状态条/清屏编排） | 产品专属版式，抽出去没有第二个消费者 | `app/AppShell.tsx`（10.7 KB） | 宿主仓 |
| **业务 UI**（T0–T7 面板、`RightRail`） | 与阶段、字段、话术强绑定；是"产品的样子"，不是"能力" | `features/panels/*`、`RightRail.tsx`（39.3 KB） | 宿主仓 |
| `session-guard`（多端操作互斥，对应 `TR-BIZ-12`） | **待定**：机制（互斥/幂等）本身通用，但只有一个消费者；见 §5 | 未建 | 宿主仓 or 独立仓（待定） |
| `auth-access` | 既有文档 §六已写"权限认证不值得自己拆"，**用成熟轮子** | 无 | 第三方库 |

## 5. 待定项（建仓前必须先定）

| # | 待定 | 影响 | 建议 |
|---|---|---|---|
| 1 | `biz-store` 的**存储机制**是否建仓（机制可复用 / 实体定义不可复用） | 决定是否有第 13 个新仓 | 建议**建仓**（机制），实体定义留宿主。否则两套系统各写一遍存储层 |
| 2 | `session-guard` 是否独立建仓 | 决定 `TR-BIZ-12` 的归属 | 若第二个系统也是多端并发，则独立；否则留宿主 |
| 3 | 引擎仓是**一个大仓多包**还是**逐引擎独立仓** | 影响 CI 与发布成本 | 见 §2.3，建议大仓多包 |
| 4 | `policies/*` 用**数据（JSON）**还是**代码（TS 包）**表达 | 影响第二个系统接入成本 | 数据优先（JSON + 校验）；需要计算时再给代码包 |
| 5 | 引擎的语言栈（TS 还是 C++） | 影响是否能与 `device-ingest` 等同构 | 阶段/评分/台账/组图都是**前端状态**，建议 **TypeScript**；`geo-data` 服务端部分随宿主语言 |
| 6 | `mapApp` 何时冻结、新宿主仓何时立 | 决定迁移窗口 | 业务引擎必须在 `mapApp` 冻结**之前**抽出，否则要迁移两次 |

## 6. 建仓顺序建议

```
第 1 批（无依赖，可立刻开工）
  geo-data            全新仓，需求专篇已就绪
  media-player        从 VideoPanel.tsx 抽离后建仓

第 2 批（先拆后端单体，再建仓）
  mission-engine      从 Api.cc 拆出 6 个引擎包（C++）
    ├─ phase-engine       先拆它（其余引擎的接口都带"当前阶段"入参）
    ├─ resource-alloc     ← Api.cc L531–576 + Seed.cc
    ├─ entity-ledger      ← Api.cc L712–759
    ├─ topology           ← Api.cc L648–709
    ├─ scoring            ← Api.cc L577–645
    └─ view-composer      ← 全新（现有映射错放在 map-2d/src/core/displayMode.ts）
  llm-provider        从 ai/rules.py 拆出规则 + ai/bridge.py 收边界（Python 独立仓）

第 3 批（依赖第 2 批的实体形状）
  alert-engine
  report-engine
  selfcheck
  （+ 待定：biz-store 机制、session-guard）

不动
  device-ingest / realtime-hub / telemetry-store / map-2d / assembly-host
```

**为什么 `phase-engine` 排第一**：其余引擎的方法签名几乎都带"当前阶段"这个参数
（对齐 `模块划分与缺口分析.md` §3.1：阶段推进的前置条件必须是引擎内的显式表）。
它不定，其它五个的接口就定不下来。

## 7. 建仓前置清单（每建一个仓都过一遍）

- [ ] 一句话说清"它单独解决什么问题"，且**不需要提本项目**
- [ ] 公开接口全清单（唯一入口，无内部路径）
- [ ] 公开接口里**检索不到**消费者专有名词
- [ ] 反向接口（需要宿主定制的地方都是注入的，不是写死的）
- [ ] 空环境 clone → 一条命令构建 → 一条命令跑独立示例
- [ ] 自带测试，不依赖宿主数据库与配置
- [ ] 独立验收脚本，退出码 0/1，可进 CI
- [ ] 零跨仓 import（尤其禁止引擎 ↔ 宿主、引擎 ↔ 引擎内部）
- [ ] 有配套工具（造数 / 压测 / 夹具）
- [ ] `README` 首屏能回答：做什么 / 不做什么 / 怎么接 / 怎么验
- [ ] 遵守 `DISC-04`：宿主里不许有业务判断；反过来，**引擎里不许有本项目专有语义**
