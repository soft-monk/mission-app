## 0.5 模块增删决策（v0.2 新增 · 本次授权后可定）

> 授权：模块可自由改、可再拆独立模块。**但拆分的判据不变**——「单独拿走它，别人能用它做完一件完整的事吗？」
> 拆出去的东西必须**零业务**、**接口里不出现本项目专有名词**。技术分层（controller/service/dao）不算模块。

### A. 拆成独立新仓（2 个）

| 新模块 | 判据（拿走能做什么） | 为什么该独立 | 依赖 |
|---|---|---|---|
| **`sim-source`**<br>仿真与感知源 | "编队航路规划 + 实体运动学 + 时间推进"——任何要在地图上放会动的实体的项目都要它 | **`device-ingest` 已经预留了这个位置**：其 `device_source.h` 明确写「模块只管收发解析归一；**演示数据长什么样是主仓的业务模拟（BusinessSim）**」，并给了 `IDeviceSource` 反向接口。做成独立模块**正是它设计时预留的接缝**，不是违背其边界 | 无（只认中立结构 + 注入时钟） |
| **`sensor-model`**<br>传感器探测模型 | 按「平台位姿 + 目标状态 + 传感器参数」给出**探测概率、可见性、覆盖多边形、重访周期** | 这是**独立于本项目的领域知识**（任何传感器仿真/融合项目都要），且 `sim-source` 不该内置它——否则想换探测模型就得改仿真引擎 | 无 |

### B. 不拆（明确记录理由，避免"为拆而拆"）

| 候选 | 为什么不拆 |
|---|---|
| 本地配置装载/校验 | 薄，且与场景强绑定 → **作为 `mission-app/packages/scenario-data`**（宿主包）。但**从一开始就给它干净公开面**，将来真有了第二个消费者可原地抽成仓 |
| 地图样式配置解析（`个性化需求` 1/2） | 不是模块，是**宿主侧配置 + `map-2d` 能力**；薄逻辑并入 `scenario-data` |
| 启动/自检仿真 | 本质是 `sim-source` 的一次调用，不独立 |

### C. 改既有模块（3 类，共 6 处）

| # | 模块 | 改动 | 理由 | 类型 |
|---|---|---|---|---|
| **M1** | `map-2d` | **位图图标（PNG）支持** + 缺省回落为"点"且**点的大小/颜色可配** | 个性化需求 1。核实：`map-2d` 只有 `registerSymbol()`（自绘 SVG），**无位图入口** → 必须改 | 新增可选能力 |
| **M2** | `map-2d` | **轨迹线宽可配** | 个性化需求 2。核实：有 `dashed`，**无线宽** → 必须改 | 新增可选字段 |
| **M3** | `map-2d` | 中文地名渲染支持（若走矢量注记） | 个性化需求 3。若底图瓦片自带中文注记则**无需改**（优先走数据侧） | 待定 |
| **M4** | `entity-ledger` | **任务执行状态机扩展**：前往 IP → 进入 IP → 目标跟踪 → 俯冲攻击 / 前往评估位 → 进入评估航线 → 评估 | Excel 步 10。**优先用规则包加动作**（它已支持规则声明动作集）；只有状态语义不足时才改代码 | 规则优先 |
| **M5** | `scoring` | 打击方案加字段：**协同方式（同时/序贯）、预计完成时间、IP 点、评估航线** | Excel 步 8–9。**改规则包 `planTemplates` 即可**（加字段属 MINOR），不动代码 | 规则包 |
| **M6** | `resource-alloc` | 集群组成加 **`altRange`（飞行高度范围）** | Excel 步 5。**改规则包** | 规则包 |

**改动纪律（沿用既有 DISC）**：
1. 改模块**在自己的仓里改**，附需求条目与验收；**不在 `mission-app` 里绕过**
2. 每个改动**可机检**（如 M1/M2 要有"给了图标就用图标、没给就画点"的断言）
3. 改完**该模块的验收脚本必须仍全绿**——这是"可复用"没被破坏的证据
4. 改动**只增不改**（新增可选字段/可选能力），破坏性变更须走各模块自己的需求流程

### D. 新增需求采纳（v0.2）

| 来源 | 采纳 |
|---|---|
| 个性化 1：图标可配（png/点）、点的大小颜色可配 | ✅ 采纳 → **M1**；配置项进 `scenario-data` 的 `map-style.json` |
| 个性化 2：航迹粗细 + 虚/实线可配 | ✅ 采纳 → **M2**（虚线已支持）+ 配置文件 |
| 个性化 3：本地地图中文地名 | ✅ 采纳 → 优先**数据侧**（找中文注记瓦片），必要时 **M3** |
| 个性化 4：Excel 迭代闭环 | ✅ 采纳为**流程约定**：每轮迭代给 Excel 与实现**同步打 tag**（v1、v2…），否则几轮后无法追溯"哪版代码对应哪版交互表" |
| 授权：模块可自由改 | ✅ 采纳 → §C 的 6 处改动**不再受"冻结"限制**，但仍走各自仓的需求流程 |
| 授权：可再拆模块 | ✅ 采纳 → §A 的 2 个新模块；§B 明确记录**不拆**的理由 |

## 1. 三个关键决策（先定这三条，其余都能推导）

### D1 · 新仓库用「一仓多包」，引擎作为依赖引入

```
mission-app/                       ← 新应用仓（业务层 + 宿主层）
├─ packages/
│   ├─ host/          宿主内核：装配、生命周期、REST/WS、反向接口实现
│   ├─ adapters/      10 个引擎 → 本项目的适配（**业务改造集中在这里**）
│   ├─ scenario-data/ 本地配置装载/校验（4 类数据 + 地图样式）
│   └─ sim-bridge/    sim-source + sensor-model 的装配与节拍驱动（薄）
├─ apps/
│   └─ web/           前端（React + map-2d + 11 步界面）
├─ policies/          规则包（各引擎的 mapapp 命名空间）
└─ data/scenario-1/   本地演示数据（4 类配置 + 地图样式）
```

**两个新模块另立仓**（§A）：`sim-source`、`sensor-model`，同样 `add_subdirectory` 原地引用。

**引擎怎么引**：`add_subdirectory` 原地引用（与 `assembly-host` 的既有做法一致），**不复制源码**。

**业务改造放哪**：优先在 `adapters/`。只有当引擎**确实缺能力**时才改引擎（§0.5-C 的 M1–M6 就是这种情况），改动要遵循各引擎自己的需求流程。

> 为什么不把引擎代码搬进新仓：搬运后"模块可独立复用"这个前提当场失效，而且 10 个引擎的验收脚本会一起失灵。

### D2 · 仿真源走 UDP，复用 `device-ingest` 全链

`device-ingest` 已有 `device_sim.exe`（发包器）与完整 pipeline（acc→prs→nrm→hlt→fan）。

| 方案 | 评价 |
|---|---|
| **A. 仿真源发包 → UDP → `device-ingest` → 宿主** ✅ 推荐 | 复用整条已验证链路（含解析、归一化、设备健康、丢包乱序统计）；现场"拔掉仿真器"即可接真设备 |
| B. 仿真源直接调宿主的 `ISink` | 简单一半，但**绕过 `device-ingest`**，"接实装就能用"的论证没了 |

**建议 A**：`device_sim` 已证明可行，新增的只是"按配置文件产生有业务含义的航迹与目标"。

### D3 · 本地文件是唯一数据源，且**热可改**

4 类数据全部来自 `data/scenario-1/*.json`，**改文件即改演示**，不需要重编译。Schema 见 §3。

## 4. 两个新模块设计（**v0.2 的主要新增工作量**）

### 4.1 `sim-source` · 仿真与感知源（新仓）

**它解决什么**：没有实装设备时，地图上会动的实体、以及"传感器看到了什么"，从哪来。

| 做 | 不做 |
|---|---|
| 编队航路规划（部署区 → 任务区，**避让 hard 禁飞区**） | 🚫 不做协议收发（`device-ingest`） |
| 实体运动学：位置/航向/速度/电量按注入时钟推进 | 🚫 不做渲染（`map-2d`） |
| 节拍控制：实时 / 倍速（1× 8× 60×）/ 暂停 / 单步 | 🚫 不做业务判断（阶段、评级、编组） |
| 目标运动（静止 / 航线 / 中途出现） | 🚫 **不内置探测模型**（交 `sensor-model`） |
| **事件出口**：逐字段等于 `device-ingest` 归一化对象 | 🚫 不查业务表（**这正是 `device_source.h` 警告过的坑**） |

**关键接缝**：产出走 `device-ingest` 的 `IDeviceSource` 语义（中立结构）+ UDP 发包，或直接经宿主 `ISink`。
**为什么它该独立**：`device-ingest` 的 `device_source.h` 已把"演示数据长什么样"划给主仓业务模拟；做成独立模块是**落实那个边界**，其他项目拿它能做"无设备演示"。

**公开面（草案）**：
```
loadScenario(scenarioJson, airspaceJson)   // 中立结构，不是业务表
setSpeed(1|8|60) / pause() / step(dtMs) / resume()
planRoutes()                                // 避让禁飞区后的 waypoints
tick(nowMs, sink|emit)                      // 推进并产出事件
attachSensorModel(ISensorModel*)            // 见 4.2（注入，不内置）
```

### 4.2 `sensor-model` · 传感器探测模型（新仓）

**它解决什么**：给定平台位姿与目标状态，**传感器能不能看见、看见的概率多大、覆盖哪里、多久重访一次**。

| 做 | 不做 |
|---|---|
| 光电 / 雷达 / 电子 三类传感器的**探测概率**（距离、方位、遮蔽、目标类型） | 🚫 不做平台运动（`sim-source`） |
| **可视性判定**（含简单地形/遮蔽，可选） | 🚫 不做时间推进与节拍 |
| **覆盖多边形**与**重访周期**计算（供 Excel 步 6 的"覆盖率/遍历周期"） | 🚫 不做融合与台账（`entity-ledger`） |
| 参数化：探测距离、视场角、扫描周期、虚警率、检测门限 | 🚫 不内置具体传感器型号参数（属规则包） |

**为什么它该独立**：这是**跨项目的领域知识**；把它从 `sim-source` 里分出来，才能"换探测模型而不改仿真引擎"。
**Excel 步 6/7 直接受益**：覆盖率、遍历周期、目标发现数量都由它算，而不是编数。

```
interface ISensorModel {
  Observation sense(const PlatformPose&, const TargetState&, const SensorSpec&, int64_t nowMs);
  Coverage cover(const PlatformPose&, const SensorSpec&, int64_t nowMs);   // 覆盖多边形
  double revisitPeriodMs(const SensorSpec&);
}
```

### 4.3 两者与既有模块的边界

```
scenario-data ──中立结构──▶ sim-source ──ISensorModel──▶ sensor-model
                                 │                            │
                                 │ 归一化事件                  │ 观测/覆盖
                                 ▼                            ▼
                          device-ingest ──▶ 宿主 ──▶ entity-ledger / topology
```

**三条硬约束**：① 二者都**不查业务表**、**互不 import**；② 都**只用中立结构 + 注入时钟**（确定性可复现）；③ 参数一律住规则包。

| **A15** | `nodes`/`entityTypes` 之外的**命名权威方向**（本轮连带确认） | **一律"规则包定词汇，数据只引用"**：凡数据里出现 key（型号、实体类型、状态、图层组、模式、探针…），其取值 MUST 能在对应规则包里找到同名声明；对不上就是**数据缺陷**，MUST NOT 靠宿主做映射表兜底 | 这条是 A14 的一般化。P1 期间 `targets.json` 的 note 已经写着"typeKey 对齐 entity-ledger 规则包"，而实际取值**没对上** —— 说明"文档声明"不能代替"机检"；后续每加一处键引用，验收脚本都要做**双向一一对应**断言（P5 的 IP 点/评估航线已这么做） |

| **A16** | **界面词汇表住在哪**（P8 收尾：用户点出"宿主源码里还有中文业务词"） | **一律进配置，源码里只留键**：① 11 步的**显示名** → `mission-app/config.json` 的 `flow.steps[]`（`step/key/title/phase`）；② 流程自产物的**文案**（时间轴分段名 / 俯冲区名 / 缺几何占位名）→ 同文件的 `flow.labels{}`。宿主源码里只剩 `key`/`phase` 骨架与 `labelOf(key)`；配置缺某条 → **回落成键名**（MUST NOT 在源码里补中文兜底）。验收加两条守卫：**S1**（标识符层：注释与字符串字面量都剥掉后不得出现业务词）、**S1b**（字符串里的业务词只许出现在**诊断载体**里：`notes`/`reason`/`message`/`basis`/`formula`/`criteria`/`baseline`/`source`/`putBlock`/`snapshot`/`cerr` …） | A15 的延伸：A15 管"**数据**里的键要对齐规则包"，这条管"**宿主源码**里不许长出词汇表"。P7 之前 11 步标题就是源码里的常量表 —— 客户改一个界面词要重新编译宿主；而 S1 当时只能靠"顺手扫注释"才变绿（假绿）。改后改 `title`/`labels` 重启即生效，守卫也成了真判据：**词汇表式的字面量**一出现就红，诊断文案（算式/判据/出处）不受影响 |
| **A17** | **界面上的"下一步"到底发什么**（手点演示暴露：三处推进在界面上根本没有入口，一处被挡住） | 一律走**阶段推进**：`mission.advance{to:"T?"}`，由宿主按阶段映射步号（T1→4 / T2→6 / T4→7 / T5→8 / T6→10 / T7→11）。**跨中间阶段的按阶段图的边依次发**（步 6 → 步 7 = 先 `T3` 再 `T4`：`phases.json` 里 T2 的 next 只有 T3）。被 Gate 挡下时：界面**照抄**引擎的 `unmet/skippedGates`，并给一颗**显式**的【强制推进（force）】—— force 只在那之后出现，是**操作员的越权决定**（引擎审计记 `force-advance / violation=true`），不是默认行为 | 手点演示发现三个**真卡点**：① 步 2 的【进入任务 ≫】被"自检全绿"挡住，而"通信链路"在真实环境里恒红 → 流程根本进不去；② 步 5 → 步 6 界面上**没有任何按钮**（宿主注释写"由宿主推进"，实际没有任何 verb 会把 step 置 6）；③ 步 7 → 步 8、步 9 → 步 10 同样没有前进入口。修法：入口一律补成 `mission.advance`（**不是** `flow.goto` —— 它只换屏、不动阶段，会让报告里的阶段与屏对不上）；自检的"全绿才准入"改为"**如实显示 + 允许带病进入**"（体检不是闸门）。改后手点 11 屏一次走通（真机脚本只用界面按钮，实测全程无需 force） |
