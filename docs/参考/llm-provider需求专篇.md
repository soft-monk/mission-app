# llm-provider · LLM/ASR/TTS 提供方抽象引擎需求专篇

- 版本：v0.1（立项稿）
- 定位：把**"大模型/语音服务怎么接、连不上怎么办、意图怎么路由到动作"**抽为一个**独立可复用引擎**，供建仓、实现与验收直接使用
- 需求编号体系：`LLM-<域>-<序号>`；域见 §3

  - 本引擎与其它九个不同：**它的实现主体在 Python**（`ai/bridge.py`，958 行，已实现得相当完整）

## 0. 完成情况总览

> 一句话：**共 39 条需求，全部 ⏳**（本专篇为立项，尚未开工）。
> **本引擎是十个引擎里"实现最完整、但边界最乱"的一个**：provider 抽象与降级已经做对了，**业务话术与意图表却混在里面**。

**现有资产映射**

| 现有实现 | 位置 | 已有（**质量高**） | 缺什么（**边界问题**） |
|---|---|---|---|
| `bridge.py` | `mapApp/ai/bridge.py`（958 行） | 仅监听 `127.0.0.1:8090`（对外地址打警告）；LLM 优先、规则兜底、**任何外网异常都不返回 5xx**；`/health` 返回能力可用性 `{status, llm, stt, tts}` | **这个模块本身没问题**，它就是"提供方抽象"的正确形态 |
| `/chat` | `bridge.py` | `{missionId?, scene, prompt, context?}` → `{text, provider:"llm"\|"rule", intent, plan?, plans?}` | — |
| `/stt` | `bridge.py` | 无 Key 时返回 `{text:"", provider:"unavailable"}` + **HTTP 200**（不报错） | — |
| `/tts` | `bridge.py` | 无 Key 时返回**本地合成音频**（有 ffmpeg 转 mp3，否则 WAV）+ HTTP 200 | 前端每条消息 `new Audio()` 无复用（`useStore.ts` L523） |
| `rules.py` | `mapApp/ai/rules.py`（与 bridge 同目录） | `INTENT_RULES`（L457 起，**大段意图表**）、`VOICE`/`VOICE_SPEAKER`/`voice_line()`（L101–196）、`PLANS`（L225 起，**三套方案逐字**）、`RECOMMEND_SCORE = {S1:93, S2:93}`（L664）、`FALLBACK_TEXT`/`PLAN_TEXT`（L652–666）、`answer()`/`match_rule()`（L699–771） | **这些全是"规则"（业务话术 + 方案台账 + 意图表），不该长在 provider 里** —— 见下方关键差距 |
| C++ 代理 | `backend/src/api/Api.cc` L102–177 | `proxyToAi` / `proxyToAiBinary`；**60 s 超时**；桥返回含 `code` 则原样透传，否则**套统一信封** `{code,message,data}`；错误码 `2001`（不可用）/`2002`（错误/非 JSON） | **每次请求 `newHttpClient`**，不复用连接（L106、L158） |
| 前端语音 | `useStore.ts` `speak()` L509–534 | TTS 优先、**失败或无音频能力时静默展示 2.4 s**（不影响界面）；`ask()` L490–502 带时间线降级提示 | `new Audio()` 每次新建、无复用；无中断/排队 |
| 前端对话 | `useStore.ts` `timeline` L68、`pushTimeline` L504–507 | 对话行（**60 条上限**）、`kind ∈ {system,user,reply,tip}` | 对话编排是业务规则 |
| 语音形态 | 初稿 §3.2 / §10.11 | 两种形态（右下角麦克风 / 页内对话行）**尚未统一** | 形态统一属规则/界面 |

**关键差距（本专篇主要价值 —— 这是一个"位置错了"的问题）**

> `rules.py` 里装着四类**纯业务规则**：
>
> | 内容 | 位置 | 为什么不该在 provider 里 |
> |---|---|---|
> | **意图表**（大段 `INTENT_RULES`） | `rules.py` L457–648 | 换一套系统，用户会说的话完全不同 |
> | **话术**（`VOICE` / `voice_line()` / `FALLBACK_TEXT` / `PLAN_TEXT`） | `rules.py` L101–196、L652–666 | 中文文案是产品内容 |
> | **方案台账**（`PLANS`，三套方案逐字） | `rules.py` L225–385 | **与 `scoring` 引擎重复**！方案名与成功率是同一份数据的两个副本 |
> | **推荐评分**（`RECOMMEND_SCORE = {S1:93, S2:93}`） | `rules.py` L664 | **与 `scoring` 引擎冲突**：93% 是算出来的还是写死的？ |
>
> 这四条正好印证了 [`模块划分与缺口分析.md`](./模块划分与缺口分析.md) §3.8 的判断：
> **LLM 是可选增强，不是依赖** —— 所以 provider 里应当只有"怎么调模型、调不通怎么办"，
> 而"说什么、推荐什么、多少分"必须回到规则包与 `scoring`。
>
> **`RECOMMEND_SCORE` 与 `scoring` 的冲突是本项目最需要先裁决的数据口径问题之一**：
> 同一个 93%，两个模块各有一份来源。

## 1. 定位与边界

### 1.1 定位

```
调用方：宿主/前端（chat / stt / tts）
   │
   ▼
┌──────────────────────────────────────────────────────────┐
│  llm-provider（Python 主体 + C++ 代理）                    │
│  PROV 提供方抽象（LLM/ASR/TTS 可替换） →                    │
│  FALLBACK 降级（超时/无 Key/报错 → 规则兜底或中性返回） →     │
│  INTENT 意图路由（把识别/输入映射到动作名） →                │
│  CONV 对话编排（三段式：系统提示 → 用户 → 回复）             │
│                      │                                   │
│                      └──► 出口：结构化结果（含 provider 标记）│
└──────────────────────┬───────────────────────────────────┘
                       │ 文本/音频 + provider 标记
                       ▼
   宿主：转成 timeline 对话行 ｜ scoring：提供确定性结论供转述
```

**一句话**：llm-provider 回答"**怎么接模型、连不上怎么办、这句话想干什么、这轮对话该谁说**"。
它**不决定业务结论**（分数来自 `scoring`、目标来自 `entity-ledger`）、**不含话术**（属规则包）、**不画界面**。

### 1.2 为什么必须是独立引擎

1. **它是唯一可以把"在线 AI"变成"可选增强"的地方**：`TR-VOI-06` / `TR-AI-02` 都要求"API 异常时核心功能不受影响"——只有把 provider 抽出来，降级才能被独立验证。
2. **换供应商不改业务**：`TR-AI-04` 要求"供应商可替换"。现状已经不差，但**规则混在里面，换供应商时会被一起带走**。
3. **它有两个消费者**：任何要接 LLM/语音的项目都能用它（这是十个引擎里**最通用的一个**）。
4. **它的接口跨语言**：Python 主体 + C++ 代理 + 浏览器消费，边界必须写死。

### 1.3 范围边界

| 做 | 不做 |
|---|---|
| 提供方抽象：LLM / ASR / TTS 各自可替换，可同时存在多实现 | 🚫 不含任何中文话术与提示文案（属规则包） |
| 降级链：超时 / 无 Key / 报错 → 规则兜底或中性返回，**永不抛 5xx** | 🚫 不含意图表内容（意图**机制**在此，**清单**属规则包） |
| 意图路由机制：把文本映射到规则声明的意图与动作名 | 🚫 不做动作执行（比如"进入 T5"由 `phase-engine` 裁决） |
| 对话编排：三段式对话行状态机（系统提示/用户/回复/提示） | 🚫 不做业务结论（分数/评级/优先级来自其它引擎） |
| 能力探测：`/health` 返回 llm/stt/tts 可用性 | 🚫 不做界面渲染（对话行与麦克风按钮属宿主） |
| 音频输出管理：合成结果返回、格式协商、失败降级 | 🚫 不做音频播放（浏览器 `<audio>`） |
| 超时、重试、并发保护、配置与密钥来源 | 🚫 不做鉴权体系（`auth-access`） |

### 1.4 硬约束

| 约束 | 取值 | 依据 |
|---|---|---|
| **仅本机监听** | AI 桥 MUST 只监听 `127.0.0.1:8090`；改成对外地址 MUST 打警告日志 | 契约 §1；`bridge.py` L11 硬性行为 1 |
| **永不 5xx** | 任何外网异常（超时/报错/无 Key）MUST 静默降级，**MUST NOT 返回 5xx** | `bridge.py` L12–15 硬性行为 2 |
| 接口形状 | `/api/v1/ai/chat` → `{text, provider:"llm"\|"rule", intent?, plan?, plans?}`；`/ai/stt` → `{text, provider}`；`/ai/tts` → 音频字节（`audio/mpeg` 或 WAV） | 契约 §3.8；`bridge.py` docstring |
| 信封处理 | 桥返回含 `code` 则原样透传，否则 C++ 代理套 `{code,message,data}` | `Api.cc` L139–147 |
| 错误码 | `2001` AI 桥不可用；`2002` 桥错误/非 JSON | `Api.cc` L122/129/150 |
| 超时 | 代理侧 **60 s**；桥侧内部超时另配 | `Api.cc` L152/176 |
| 密钥来源 | `config.json` → 环境变量覆盖（`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `AI_BRIDGE_*`）；**密钥 MUST NOT 进前端** | `bridge.py` L16；TRD §3.1 |
| STT 降级 | 无 Key MUST 返回 `{text:"", provider:"unavailable"}` + HTTP 200 | `bridge.py` L14 |
| TTS 降级 | 无 Key MUST 返回本地合成音频（ffmpeg → mp3，否则 WAV）+ HTTP 200 | `bridge.py` L15 |
| 麦克风前置 | 浏览器 `getUserMedia` 需 secure context；内网 HTTP 下 Chromium 默认拒绝 → 需 HTTPS 或评估国产化浏览器 | TRD §4.6 技术前置 ⏸ |
| 对话行上限 | 前端保留 60 条（界面行为） | `useStore.ts` L506 |

## 3. 功能需求条目

### 3.1 提供方抽象（LLM-PROV）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| LLM-PROV-01 | **MUST** LLM / ASR / TTS 三类能力各自有提供方接口，实现可替换且可并存多实现 | 换一个 LLM 实现只改装配；内核零改动 | ⏳ |
| LLM-PROV-02 | **MUST** 能力探测：`/health` 返回 `{status, llm:bool, stt:bool, tts:bool}`，**探测 MUST 真实反映可用性**（不是配置推断） | 拔掉 Key → `llm:false`；恢复 → `true` | ⏳ |
| LLM-PROV-03 | **MUST** 配置与密钥来源分层：文件 → 环境变量覆盖；**密钥 MUST NOT 出现在响应、日志、前端** | 全仓检索密钥明文零命中；响应中无密钥字段 | ⏳ |
| LLM-PROV-04 | **MUST** 仅本机监听，非本机地址 MUST 打警告（保留现有行为） | 配成 `0.0.0.0` 时日志有警告 | ⏳ |
| LLM-PROV-05 | **MUST** 连接复用：C++ 代理 MUST NOT 每请求新建客户端（现状 `Api.cc` L106/158 每次 `newHttpClient`） | 连续 100 次调用，连接数与耗时显著下降 | ⏳ |
| LLM-PROV-06 | **SHOULD** 多实现路由：可按场景/能力路由到不同提供方（如演示用规则、生产用模型） | 路由规则可配、可复现 | ⏳ |

### 3.2 降级链（LLM-FALLBACK）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| LLM-FALLBACK-01 | **MUST** 永不 5xx：任何外网异常（超时/HTTP 错误/无 Key/解析失败）MUST 降级，**MUST NOT 返回 5xx**（保留现有承诺） | 断网、错 Key、超时三种注入下均返回 200 且有可用内容 | ⏳ |
| LLM-FALLBACK-02 | **MUST** `provider` 字段如实标注来源（`llm` / `rule` / `unavailable`），**MUST NOT 伪装** | 降级时 `provider` 不为 `llm` | ⏳ |
| LLM-FALLBACK-03 | **MUST** 降级内容可用：LLM 不可用时 MUST 由规则兜底给出**有效回答**（现状 `rules.py` `FALLBACK_TEXT`/`answer()` 已实现） | 断 LLM 后核心对话仍可走通（`TR-VOI-06`） | ⏳ |
| LLM-FALLBACK-04 | **MUST** 超时分离：桥内部超时与代理侧 60 s 超时 MUST 分别可配，且内部超时 MUST 早于代理超时（避免代理先断） | 人为制造慢响应 → 桥先降级返回，代理不报 2001 | ⏳ |
| LLM-FALLBACK-05 | **MUST** STT 降级语义：无 Key → `{text:"", provider:"unavailable"}` + 200（保留现状） | 无 Key 时前端可判断并提示，不崩 | ⏳ |
| LLM-FALLBACK-06 | **MUST** TTS 降级语义：无 Key → 本地合成音频 + 200（保留现状）；本地合成 MUST 可配（音调/静音、时长） | 无 Key 时前端仍听到提示音而非报错 | ⏳ |
| LLM-FALLBACK-07 | **SHOULD** 降级可观测：降级次数、原因分布可查（供排障与演示前检查） | 可读出降级计数 | ⏳ |

### 3.3 意图路由（LLM-INTENT）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| LLM-INTENT-01 | **MUST** 意图**清单**由规则提供（意图 id、示例话术、目标动作名），引擎 MUST NOT 内建任何意图与话术 | 换规则即换意图集；全仓检索 `"推荐一个任务模式"` 零命中 | ⏳ |
| LLM-INTENT-02 | **MUST** 匹配策略分层：先**规则匹配**（确定、可复现），再**模型兜底**（泛化）；结果 MUST 标注用了哪一层 | 同一句话两次匹配结果一致；未命中时走模型 | ⏳ |
| LLM-INTENT-03 | **MUST** 场景别名归一：同一意图在不同场景下的表述差异 MUST 由规则声明（现状 `SCENE_ALIASES`/`normalize_scene` 已实现） | 别名表可配、可复现 | ⏳ |
| LLM-INTENT-04 | **MUST** 未识别兜底：未命中任何意图时 MUST 返回明确"未识别"而非沉默（**MUST NOT 猜**） | 输入乱码 → 返回未识别 | ⏳ |
| LLM-INTENT-05 | **MUST** 意图只路由不执行：引擎返回动作名与参数，**执行由宿主 / 对应引擎裁决** | 引擎内无阶段推进、无落库 | ⏳ |
| LLM-INTENT-06 | **SHOULD** 指令集可导出：可导出全部意图与示例话术（支撑初稿 §10.4"指令集清单文档化"） | 一次调用导出完整清单 | ⏳ |

### 3.4 对话编排（LLM-CONV）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| LLM-CONV-01 | **MUST** 三段式状态机：系统提示 / 用户输入 / 回复；**谁在说 MUST 可判定**（现状 `VOICE_SPEAKER`/`speaker_of()` 已实现） | 三段的说话方可查询 | ⏳ |
| LLM-CONV-02 | **MUST** 话术内容由规则提供，引擎 MUST NOT 内建任何成句文案（现状 `VOICE`/`voice_line()` 在 `rules.py`，**应移入规则包**） | 全仓检索话术零命中于引擎源码 | ⏳ |
| LLM-CONV-03 | **MUST** 对话行上限可配且不丢关键行：超出上限时 MUST 保留最新（前端现状 60 条，保留语义） | 灌 100 条 → 保留最新 60 条 | ⏳ |
| LLM-CONV-04 | **MUST** 播报与展示分离：`speak` 标志决定是否合成语音；**合成失败 MUST 不影响文本展示**（保留现状"静默展示 2.4 s"） | 无 TTS 时文本照常显示 | ⏳ |
| LLM-CONV-05 | **MUST** 语音状态机：`idle`/`listening`/`speaking` 等状态可查询，且与 `voice.state` 事件一致 | 状态迁移可复现 | ⏳ |
| LLM-CONV-06 | **MUST** 打断与排队：新的播报 MUST 能打断当前播报（或按可配策略排队），**MUST NOT 叠音** | 连续两次 speak → 不叠音 | ⏳ |
| LLM-CONV-07 | **SHOULD** 音频对象复用：TTS 结果 MUST 复用播放器实例并可缓存（现状每条 `new Audio()`，`useStore.ts` L523） | 连续播报 20 次，音频对象创建次数显著下降 | ⏳ |

### 3.5 与其它引擎的边界（LLM-BOUND）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| LLM-BOUND-01 | **MUST** 移除 `rules.py` 的 `PLANS`（三套方案台账）：方案定义 MUST 唯一来自规则包，**MUST NOT 在 provider 里有副本** | 全仓检索方案名 → 只在规则包中出现 | ⏳ |
| LLM-BOUND-02 | **MUST** 移除 `RECOMMEND_SCORE = {S1:93, S2:93}`：推荐分数 MUST 唯一来自 `scoring` 引擎 | 全仓检索 `93` 作为评分常量零命中；分数可溯源到 `scoring` | ⏳ |
| LLM-BOUND-03 | **MUST** provider 只做"转述"：结构化结论由 `scoring` / `entity-ledger` / `topology` 提供，provider MUST NOT 自行生成业务数值 | 断掉 `scoring` → provider 返回缺失标记而非编造 | ⏳ |
| LLM-BOUND-04 | **MUST** 与 `alert-engine` 区分（对齐 `alert-engine` D2）：`ai.event` 是提示/播报（无台账），`alert` 是需处置告警；**两者 MUST NOT 互相替代** | 提示不写入告警台账；告警不降级为纯文本提示 | ⏳ |
| LLM-BOUND-05 | **MUST** 与 `scoring` 的分工：`scoring` 出确定性评分与理由条目，provider 把**理由条目**转成话术；**MUST NOT 由模型决定分数** | 同一输入下分数不因模型变化而变 | ⏳ |
| LLM-BOUND-06 | **SHOULD** 意图 → 动作的映射表可枚举（供宿主注册动作处理器） | 映射表可导出 | ⏳ |

### 3.6 非功能性（LLM-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| LLM-NFR-01 | **MUST** 独立交付：Python 侧独立运行（不依赖 C++ 后端与前端）、独立示例、独立测试、独立验收脚本 | 空环境安装依赖 → 一条命令起服务 → 一条命令跑验收 | ⏳ |
| LLM-NFR-02 | **MUST** 零业务依赖：引擎源码内不出现方案名、阶段名、区域名、具体话术 | 全仓检索零命中（规则包除外） | ⏳ |
| LLM-NFR-03 | **MUST** 无外网也能起：无 Key / 断网时服务 MUST 正常启动并提供降级能力 | 断网启动成功，`/health` 返回 `llm:false` | ⏳ |
| LLM-NFR-04 | **MUST** 不阻塞主链路：AI 不可用 MUST NOT 影响实时通道（WS）与业务接口 | 断开 AI 桥后业务接口与 WS 正常 | ⏳ |
| LLM-NFR-05 | **SHOULD** 性能：规则路径 P95 ≤ 50 ms；LLM 路径按外部服务；TTS 本地合成 P95 ≤ 500 ms | 实测达标 | ⏳ |
| LLM-NFR-06 | **SHOULD** 并发保护：并发请求超上限时 MUST 排队或快速失败，MUST NOT 拖垮桥 | 压测下响应可预测 | ⏳ |
| LLM-NFR-07 | **SHOULD** 麦克风前置提供可行路径（HTTPS 自签名 / 国产化浏览器评估），使 STT 在目标环境可用 | 目标环境实测 STT 可用 | ⏳ |

## 4. 引擎与规则的划分（policies）

| 属引擎（可复用） | 属规则（`policies/mapapp`，项目专属） |

## 6. 风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **移出 `PLANS` 与 `RECOMMEND_SCORE` 会改变现有行为**（当前规则路径直接给 93%） | 演示数字变化 | 先让 `scoring` 产出同样的 93%（由规则配准），provider 改为转述；上线前逐屏比对 |
| R2 | 移出意图表后，规则路径的匹配能力可能下降 | 语音指令识别变差 | 意图表只是换位置（规则包），匹配机制不变；加一组"每意图至少一句"的回归用例 |
| R3 | 麦克风 secure context 前置未解决 | STT 在目标环境不可用 | LLM-NFR-07 单列；先保证文本对话与 TTS 可用 |
| R4 | 引擎被写成"通用 AI 编排平台" | 配置地狱、与 `scoring` 重叠 | 只支持三类能力 + 降级 + 意图路由 + 对话状态机；**不做 Agent 编排、不做工具调用框架** |
| R5 | 模型输出被用作业务数值 | 分数不可复现 | LLM-BOUND-03/05 用测试锁定：断开 `scoring` 时 provider 不得编造数值 |
| R6 | 密钥泄漏到前端或日志 | 安全问题 | LLM-PROV-03 验收：响应与日志检索密钥零命中 |

## 7. 验收清单

- [ ] 空环境安装依赖 → 一条命令起服务 → 一条命令跑通验收（退出码 0）
- [ ] **断网 / 无 Key 时服务正常启动**，`/health` 返回 `llm:false`（`stt`/`tts` 语义正确）
- [ ] 断网、错 Key、超时三种注入下 `chat` 均返回 200 且有可用内容，**无 5xx**
- [ ] 降级时 `provider` 不为 `llm`（不伪装）
- [ ] 桥内部超时早于代理 60 s 超时：慢响应时桥先降级，代理不报 2001
- [ ] 无 Key 时 `/stt` 返回 `{text:"", provider:"unavailable"}` + 200
- [ ] 无 Key 时 `/tts` 返回本地合成音频 + 200；本地合成参数可配
- [ ] 全仓检索方案名、`93`、阶段名、`"推荐一个任务模式"` → 引擎源码零命中
- [ ] 断掉 `scoring` → 返回缺失标记而非编造数值
- [ ] 同一句话两次匹配结果一致；未命中时走模型层并标注层级
- [ ] 输入乱码 → 返回"未识别"而非猜测
- [ ] 可导出全部意图与示例话术（支撑指令集清单文档化）
- [ ] 三段式说话方可判定；状态迁移可复现
- [ ] 灌 100 条对话 → 保留最新 60 条，关键行不丢
- [ ] 无 TTS 时文本照常展示（静默展示策略生效）
- [ ] 连续两次播报不叠音（打断或排队按配置）
- [ ] 连续播报 20 次，音频对象创建次数显著下降
- [ ] 连续 100 次调用，连接复用生效（连接数与耗时下降）
- [ ] 断开 AI 桥后业务接口与 WS 正常（不阻塞主链路）
- [ ] 响应与日志中检索密钥明文 → 零命中
- [ ] 配成 `0.0.0.0` 时日志出现对外监听警告
