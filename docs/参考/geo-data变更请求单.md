## CR-01 · CLI 生成清单时把 4 位以上的 `x` 目录整层丢掉（**静默**，且 `verify` 同盲区）

**提出者**：`mission-app` 瓦片接入（P2 期间）
**日期**：2026-09-16
**严重度**：**高**（清单看起来"通过"，但内容少了一半以上；用 `verify` 也查不出来）

### 现状

`geo-data/src/tool/manifest.cc:54` 的 `parseIntStrict` 带一个 `s.size() > 3` 的上限（本意是限制 **zoom**：z 最多 3 位），
但同一次遍历里它也被用来过滤 **x 目录名**：

```
tiles/raster/<z>/<x>/<y>.jpg      ← x 在本机数据里是 3~5 位（例：13493）
```

结果：**x ≥ 1000 的目录被静默丢弃**。本机实测（`map-2d/tiles/raster`，z0–z14，实际 14204 块）：

| 工具 | 结果 |
|---|---|
| `manifest --dir … --version v1 --keys all` | 只看到 **5545** 块（z0–z10），清单里 `total=keys=5545`，**退出码 0** |
| `verify --dir … --mode manifest` | 报「缺块 0、摘要匹配 true」，**退出码 0**（与生成器同一盲区，互相印证了错误的结论） |
| 逐目录枚举（宿主侧独立实现） | **14204** 块，z0–z14 连续 |

### 影响

- 宿主按 CLI 清单挂载后，**z11–z14 全部 404**（正是演示要用的那几级），而 `/stats` 会显示"已就绪"；
- 因为 `verify` 用同一套解析逻辑，**CI 也不会报警** —— 这是一个"工具自证一致、事实错误"的失败模式。

### 请求

| # | 请求 | 类型 | 影响面 |
|---|---|---|---|
| 1 | `x` / `y` 用**不限位数**的整数解析（`3 位上限只留给 z`），或改为按目录名逐段独立校验 | 修 bug | `src/tool/manifest.cc`、`src/tool/source.cc`（同源解析） |
| 2 | 枚举到的块数与目录实际文件数做一次**交叉核对**，不一致时 `verify` 必须报错（而不是只对清单自证） | 增强（防同类复发） | `verify` 的 `auto/probe` 两模式 |
| 3 | 补一条用例：`x` 取 4 位/5 位（如 `13493`）的瓦片必须被枚举到 | 测试 | `tests/` |

### 不阻塞项声明

- 本请求**不阻塞** `mission-app` 演示：宿主侧的清单由一次性生成器产出（枚举走 `geo_data::NativeHostFs`，
  摘要与 JSON 序列化仍走 `manifest.h` 的冻结契约），并已实测 z0–z14 全部 200。
- 但**任何第三方**用自带 CLI 生成清单都会踩到同一个坑，建议优先修。
