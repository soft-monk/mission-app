## 0. 结论先行

### 0.1 一个判断：现有五个模块全都是「管道」，没有一个是「业务」

把四个模块的 README 并排看，它们各自都写明了同一句话：

| 模块 | 一句话定位 | 明说不做 |
|---|---|---|
| `device-ingest` | "各说各话的外设，怎么变成一份标准数据？" | 不做地图、不做业务（阶段/台账/评级）、不做存储 |
| `realtime-hub` | "有数据了，怎么同时送到每个人手上？" | 不做业务判断（不认识无人机、告警、任务、编组）、不落库、不补发 |
| `telemetry-store` | "过去那段时间，这条流里到底发生了什么？" | 不做业务查询（"哪个任务完成了"去问业务数据库）、不推送、不画图 |
| `map-2d` | "宿主给数据、调接口，模块出图" | 不做业务流程与阶段规则、台账与评级、链路状态机、任务编排、界面框架 |
| `assembly-host`（MAH） | "把五个模块串成一台能跑的机器，验证它们真的互不认识" | **非目标里明确写着"业务逻辑（任务/阶段/方案/目标）属 `mapApp` 主仓"** |

也就是说：**现有五件套正好覆盖"数据链路 + 渲染"这四段（入口 → 管道 → 留存 → 出口），
需求初稿里 9 个章节的能力，一条都没落地。**

```
①入口            ②管道             ③留存              ④出口
device-ingest → realtime-hub   →  telemetry-store  →  map-2d      ← 这一条已经通了
────────────────────────────────────────────────────────────────
任务编排 / 资源编组 / 链路评估 / 目标情报 / 方案决策 / 态势组图 /
告警 / 语音 / 报告 / 自检 / 基线 / 地理数据 / 业务库  ← 全缺
```

## 1. 判定口径

### 1.1 三条选型基准（沿用现有模块的既有基准，不新造）

1. **单向依赖**：只允许 `宿主 → 模块`；禁止模块回头依赖宿主或其他模块的内部。
2. **可离线自证**：在本模块目录内、无宿主/无后端/无外网的前提下能构建、能启动、能跑验收。
3. **无内置业务耦合**：模块内不出现"别的模块的业务名词"（不是不许出现"任务"——业务模块当然有业务词，而是**不许出现别人的业务模型**）。

### 1.2 判定方法

对需求初稿第 9 章"功能与组件清单"的 6 大类逐条落位：

```
需求条目 ──► 是"通用能力"还是"本项目业务语义"？
              │
              ├─ 通用能力（收/存/推/画/连）────► 已有模块或 L2 基础设施
              │
              └─ 业务语义（任务/方案/集群/目标/阶段）─► 必须落在 L3 模块
                                                        ↓
                                        宿主里只留"装配 + 适配"两件事
```

### 1.3 「可复用」的判定：三把现成的尺子 + 一条机检

既有文档里已经给了判定标准，本节直接沿用，不新造口径：

| 来源 | 尺子 | 原文 |
|---|---|---|
| `模块划分_后续拆分方案.md` §二 | **拿走能用吗** | "单独拿走这个模块，别人能用它做完一件完整的事吗？" |
| 同上 §二 | **词汇表** | 出现 `任务/方案/目标/场景/阶段/编组/评估` → **业务，别抽**；只有 `设备/数据/事件/连接/时间/图层/坐标` → 真模块 |
| `map-2d/doc/需求文档-解耦版.md` M2-MZ-02-01 | **契约自足** | "只传『配置 + 空数组』即可出图；所有业务字段缺省均有定义行为" |
| 同上 M2-MZ-01-01 | **零业务名词** | "全仓检索业务名词零命中" |

**本文补一条可机检的判据（三把尺子的合并形式）：**

> **接入方在模块源码上零改动，能否用它做完一件完整的事？**
> 验收方式：把模块目录拷到空工程 → 只写自己的业务数据与配置 → 能否跑通本模块自带的示例。
> **需要改模块源码才能接进去的，都不是可复用模块。**

由此分出**四档**，而不是"可复用 / 不可复用"两档：

| 档 | 定义 | 跨项目动作 | 交付形态 |
|---|---|---|---|
| **T1 通用模块** | 全部语汇是通用词汇（设备/事件/图层/瓦片/通道/探针） | **原样拿走** | 独立仓，可开源级交付 |
| **T2 改造模板** | 内核通用，但契约里带着本项目语汇 | **克隆后改语汇**（改完它就是别人的东西） | 骨架 + 改造清单 |
| **T3 引擎 + 配置注入** | 机制通用、规则/模板/清单由宿主注入数据 | **换一份配置即可用**（零改码） | 独立仓 + 配置 schema |
| **T4 纯业务** | 语汇与规则都是本项目的（阶段/编组/评级/场景） | **不可复用**，通用化只会变成"配置地狱" | 留主仓，不必拆仓 |

> **T3 是关键发现**：`alert-center` / `report-service` / `biz-store` 这类看着像业务的模块，
> 拆对了其实是**通用引擎 + 项目配置**。判据只有一条：
> **模块的公开接口里，有没有出现本项目的专有名词** ——
> `raise(rule, context)` 通用；`raise("阶段超时", taskId, phase)` 就是业务，必须改回去。

## 3. L3 应用域模块（本次要补的重点）

### 3.0 复用性总表（回答"哪些能给别的项目，哪些不能"）

> 判定口径见 §1.3。**"现在在哪"一列是关键的现状事实** —— 复用性判断必须基于真实代码位置，
> 不能基于"它叫什么名字"。

#### 3.0.1 已有五个模块

| 模块 | 档 | 现在在哪 | 跨项目怎么用 | 结论 |
|---|---|---|---|---|
| `device-ingest` | **T1 通用** | 已独立仓 `webMap/device-ingest` | 原样拿走：多端口 UDP → 插件解析 → 归一化 → 设备健康 | ✅ 已按可复用交付 |
| `realtime-hub` | **T1 通用** | 已独立仓（`server/` + `client/` 两包） | 原样拿走：一次 broadcast 推给所有在线客户端 | ✅ 已按可复用交付 |
| `telemetry-store` | **T1 通用** | 已独立仓 | 原样拿走：时序留存 / 区间查询 / 回放 / 补发 | ✅ 已按可复用交付 |
| `map-2d` | **T1 通用** | 已独立仓 | 原样拿走：给 `MapData` 就出图，能点能画能回放 | ✅ 已按可复用交付 |
| `assembly-host` | **T2 改造模板** | `webMap/assembly-host`，**是本项目的宿主，本身不是可复用模块** | 它的**装配骨架**（`DrogonTransport` / `HubSink` / `StoreWriter` / 退出 flush 序列）可作任何"五件套装配"的克隆模板；但接入点配置、事件名、页面壳都是本项目的 | ⚠️ 骨架可复用、本体不可复用 |

|---|---|---|---|---|

#### 3.0.3 汇总：一句话答案

```
可以给别人的（T1 / T2 / T3）        ｜ 不能给别人的（T4）
──────────────────────────────────┼──────────────────────────────
device-ingest     外设接入         ｜ scenario-orchestrator  任务编排
realtime-hub      实时通道         ｜ resource-registry      资源编组
telemetry-store   时序留存         ｜ decision-engine        方案决策
map-2d            二维地图渲染      ｜ link-topology          链路拓扑
geo-data          地理数据管线      ｜ target-intel           目标情报
media-player      媒体播放         ｜ situation-layer        态势组图
sim-source(内核)   轨迹仿真         ｜ mission-baseline       场景基线
biz-store(机制)    结构化存储        ｜ biz-store(实体)        业务表
alert-center      告警引擎*        ｜ voice-interaction(意图) 语音业务
report-service    报告引擎*        ｜ auth-access(若自建)     权限模型
selfcheck         自检引擎*        ｜
assembly-host(骨架) 装配模板        ｜
──────────────────────────────────┴──────────────────────────────
* T3：换配置即可用，接口里不出现本项目专有名词
```

**一句话记住分界**：**接口里出现"任务/阶段/方案/目标/编组/场景"，就是业务层；
只出现"设备/事件/连接/时间/图层/坐标/瓦片/通道/探针"，就是可复用层。**

#### 3.0.4 三条容易搞错的边界

| 容易搞错 | 正解 |
|---|---|
| "`biz-store` 存的是我们的业务表，所以它是业务模块" | **拆开看**：`append/query/migrate` 是通用机制（T1），`任务/目标/方案` 三张表是业务定义（T4）。做成"**机制独立仓 + 主仓里的实体定义**"，别焊在一个仓里 |
| "`alert-center` 讲的是我们的告警，所以是业务" | 告警的**规则**是业务，告警的**引擎**（分级/去重/合并/确认/订阅/审计）是通用的。接口保持 `raise(rule, context)`，规则从 `mission-baseline` 注入 |
| "`sim-source` 仿真我们的无人机，所以是业务" | **轨迹运动学 + 节拍控制 + 丢包乱序注入**完全通用（任何实时上屏项目都要）；**"6 个集群按 A/B/C 区域展开"这个场景脚本**才是业务。二分即可 |

> ⚠️ **反向警示**：把 T4 强行做成"可配置的通用模块"，会得到一堆
> `phaseRules.json` / `scoringWeights.yaml` / `clusterTemplates.json` —— 表面通用，实际是**配置地狱**，
> 而且是"只有本项目能用、还更难改"的地狱。**业务模块就大方承认它是业务。**

### 3.1 `scenario-orchestrator` · 任务编排

**定位**：回答"现在处于哪个阶段、下一步能不能走、这一步的结论是什么"。

| 做 | 不做 |
|---|---|
| T0–T7 阶段定义与状态机（含进入/退出条件） | 不画图（交 `situation-layer` + `map-2d`） |
| 任务台账：任务编号、名称、类型、区域、时间、状态 | 不算方案评分（交 `decision-engine`） |
| 阶段推进与回退、分支（自检不通过、链路中断、目标丢失） | 不存库（交 `biz-store`） |
| 任务流程进度条数据（任务下达 → … → 任务完成 + 时间戳） | 不发声（交 `voice-interaction`） |
| 阶段→上下文（context）广播：供图层映射、面板显隐使用 | 不认识界面控件 |

**对外契约（草案）**

```
getTask()                        → TaskSnapshot
getPhase()                       → { phase: 'T0'..'T7', enteredAt, subStep }
advance(phase, payload)          → Result       // 校验前置条件，不满足给可读原因
rollback(phase)                  → Result
subscribe(onPhaseChanged)        → Unsubscribe
timeline()                       → PhaseNode[]  // 进度条直接用
```

**关键设计点**：阶段推进的"前置条件"必须是**模块内的显式表**（每阶段一条），不能散落在界面按钮的 `onClick` 里 —— 这是需求初稿里"底部按钮随阶段变化"能收口的前提。

**依赖**：无（只依赖 `IClock` / `ILogSink` 反向接口）。**被依赖**：几乎所有界面。

### 3.2 `sim-source` · 推演数据源

**定位**：回答"没有实装设备时，地图上动的这些点从哪来"。

这一步必须显式做，因为不做的话它会**悄悄长进宿主里**：MAH 现在用 `device_sim.exe` 发固定格式的包，
而需求里的演示数据是有语义的（6 个集群按任务区域展开、电量递减、链路质量随距离变化、目标出现/消失）。

| 做 | 不做 |
|---|---|
| 按场景基线生成四型无人机的航迹/电量/航向/速度 | 不做协议接入（那是 `device-ingest`） |
| 生成链路质量事件（信号强度、带宽、时延、丢包） | 不做渲染与业务判断 |
| 推演节拍控制：实时 / 加速 / 暂停 / 单步（配合回放演示） | 不做留存（`telemetry-store`） |
| 事件形状 = `device-ingest` 归一化契约 + `realtime-hub` 事件信封 | 不发明新事件名与字段 |

**关键设计点**：本模块是"演练/演示"角色的唯一合法来源。
它产出的事件必须**逐字段等于** `device-ingest` 的归一化对象（`{deviceId, deviceType, kind, lng, lat, alt, heading, speed, battery, seq, ts}`），
这样"接仿真"和"接实装"对下游完全对称 —— 演示能跑通，实装接上就能跑。

### 3.3 `resource-registry` · 资源与编组

**定位**：回答"我手里有什么、分给谁了、还能不能再分"。

| 做 | 不做 |
|---|---|
| 四型无人机台账（光电/雷达/电子/通信：总数、可用、已分配、待分配） | 不生成方案（方案是 `decision-engine` 的事） |
| 集群定义与组成（名称、四型配比、任务方向、覆盖区域、协同关系） | 不画集群框 |
| 分配/释放/重新编组；可用数一致性校验 | 不判断链路好坏（交 `link-topology`） |
| 用量统计：资源利用率 86%、编组 124/132、就绪率 | 不存历史（交 `telemetry-store` / `biz-store`） |
| 实时位置/电量/在线态的**汇入接口**（数据来自 device-ingest 归一化事件） | 不订阅网络（由宿主喂） |

**对外契约（草案）**

```
listDevices(type?)               → Device[]
listClusters()                   → Cluster[]
assign(clusterId, allocation)    → Result        // 校验不超可用数
release(clusterId)               → Result
utilization()                    → { used, total, rate, readyRate }
applyTelemetry(normalizedEvent)  → void          // 单点汇入，内部只更新台账
subscribe(onChanged)             → Unsubscribe
```

**关键设计点**：`applyTelemetry` 的入参形状必须**只用 `device-ingest` 归一化契约里的通用字段**（`deviceId/deviceType/kind/lng/lat/alt/heading/speed/battery/seq/ts`），
不得把"任务/方案"塞进设备事件 —— 那样 `device-ingest` 就被迫知道业务了。业务含义靠 `deviceType` 映射表（表在 `mission-baseline`）。

### 3.4 `decision-engine` · 方案决策与评估

**定位**：回答"给我三套方案、哪套最好、为什么"。

| 做 | 不做 |
|---|---|
| 三套编组方案生成（稳态侦察覆盖/多域协同压制/重点区域突破） | 不生成自然语言话术（话术交 `voice-interaction` 的 LLM 侧） |
| 三套打击方案生成（光电精确打击/多集群协同压制/电子干扰配合） | 不画方案卡（界面壳的事） |
| 确定性评分与排序：区域覆盖率、链路稳定度、目标发现效率、电子压制能力、任务成功率、资源利用率 | 不做实时控制 |
| 推荐理由条目化输出（4 条）、预期效果（6 项）、推荐评分（93%） | 不落库 |
| 自动优化：按规则扰动参数重跑评分 | — |

**关键设计点 1 —— 必须拆成两个 provider**：

```
decision-engine（确定性：规则 + 评分 + 排序，可复现、可单测）
        ▲
        │ 只读调用
voice-interaction / llm-provider（非确定性：把结构化结论转成话术）
```

现场演示不允许"AI 说 82%"，必须是"引擎算出 82%，LLM 只负责把它讲成人话"。
**这条是需求初稿 §10.3「AI 推荐方案的核心算法/规则是什么」的答案前提。**

**关键设计点 2**：评分输入必须显式声明（任务区域、资源可用量、链路评估、目标清单），
不允许在评分函数里读全局 store —— 否则无法单测，也无法回答"为什么 93%"。

### 3.5 `link-topology` · 链路拓扑

**定位**：回答"谁连着谁、这条链路好不好、能不能撑住多集群协同"。

| 做 | 不做 |
|---|---|
| 拓扑模型：自组网网状（6 集群 + 前沿指挥节点）、云边端三层（云端算力中心 → 边缘节点 → 集群） | 不收包（链路质量来自接入层归一化事件或模拟源） |
| 链路状态机：稳定/波动/受限（对应 `map-2d` 的 `LinkItem.state: green/yellow/red`） | 不画拓扑图（`map-2d` 已有 `LinkItem` / `ClusterItem` 图元） |
| 质量指标：信号强度、带宽、时延、丢包率、覆盖范围、局部组网进度、边缘节点负载、本地缓存 | 不做指令下发（属 `device-ingest` S4） |
| 网络评估四项：链路稳定度、覆盖率、协同效率、抗干扰能力 | 不做视频/图像流传输 |
| 评估结论："支持三集群并行数据回传""延迟满足实时控制要求" | 不决定阶段推进 |

**关键设计点 1**：`map-2d` 已经提供了 `LinkItem {id, from, to, state?: green|yellow|red}` 与
`ClusterItem {id, lng, lat, name}` 两类图元，**渲染侧不缺东西**。本模块补的是渲染侧不该管的三件事：

1. **拓扑的节点与边从哪来**（自组网网状 vs 云边端三层，两套结构）；
2. **节点摆在哪**（前沿指挥节点、云端算力中心、边缘节点的坐标/布局由场景给定）；
3. **状态怎么算出来**（从链路质量指标到 green/yellow/red 的判定与迟滞，避免状态抖动）。

**关键设计点 2**：模块只产出**图元可用的结构**（节点 + 边 + 边上状态码），
**颜色语义不得写死在拓扑模块里**，否则换主题/换配色要改两个模块。

### 3.6 `target-intel` · 目标与情报

**定位**：回答"有哪些目标、哪个最该打、它过去去过哪"。

| 做 | 不做 |
|---|---|
| 目标台账：编号、类型、威胁等级、来源（光电/雷达/电子/融合）、动态状态、坐标、置信度 | 不画目标符号（`map-2d` 已内置通用军事标绘符号） |
| 威胁评级规则：高/中/低 + 高价值标记（红色） | 不做毁伤判断（评估口径待定，见 §6） |
| 优先级排序与打击序列（优先级 1/2/3、加入攻击序列） | 不生成任务（交 `scenario-orchestrator`） |
| 情报关联关系链（通信节点 → 指挥节点 → 火力阵地 → …） | 不落库（交 `biz-store`） |
| 轨迹回溯数据（`-02:00 ~ +02:00` 时间轴、游标、预测轨迹） | 不做回放控件（`map-2d` 已有时间轴与播放控制） |
| **编号与类型一致性治理**（初稿 §10.12 的 T4-1/T4-2/T7-2 目标数不一致） | — |

**关键设计点**：初稿第 12 条待确认问题（目标编号跨界面不一致）**必须在本模块内一次性收口**：
定义"目标以任务为维度唯一编号，跨界面强一致"，并提供 `assertConsistency()` 供验收脚本调用。
否则同一份演示数据会在 T4/T5/T7 三个界面自相矛盾。

### 3.7 `situation-layer` · 态势组图

**定位**：回答"当前这个阶段，地图上应该出现什么"。

> 这是最容易被低估的一个模块。`map-2d` 明确"模块内无任何具体模式名清单"（M2-MZ-01-04），
> 而需求初稿里有 10 种显示模式、11 组图层、若干区域多边形与热点。
> **这中间的映射关系必须有地方放 —— 放宿主就违反 DISC-04，所以它必须是一个模块。**

| 做 | 不做 |
|---|---|
| 显示模式定义与映射表：综合态势/侦察展开/侦察融合/目标识别/任务规划/打击确认/实时态势/引导控制/复核态势/结果汇总 → 图层组合、底图、工具条、图例 | 不做渲染（调 `map-2d` 公开接口） |
| 业务标绘：A/B/C 区域、核心搜索区、重点侦察区、已覆盖区域边界、威胁热区、攻击走廊、毁伤着色 | 不做量算/绘制交互（`map-2d` 已有） |
| 把各模块输出**组装成 `map-2d` 的 `MapData`**（图层 + 图元 + 回放数据） | 不产生业务数据（只读各业务模块） |
| 地图工具条随阶段变化（选择/测距/图层/区域/新建/全屏/标绘） | 不做面板与导航（宿主壳） |
| 地图内图例四组（威胁等级/目标状态/链路状态/图元类型）的内容组织 | 不定义配色（`map-2d` 主题） |

**关键设计点**：本模块是**唯一允许同时读多个业务模块**的模块（只读、单向），
这就是"适配器文件同时 import 两个包是对的"（realtime-hub README 原话）在业务层的推广。
但要守住：**只读，不回写**。

### 3.8 `voice-interaction` · 语音与对话

**定位**：回答"系统该说什么、用户说了什么、听懂了要动谁"。

需求初稿实测的两种形态（初稿 §3.2、§10.11 明确要求统一）：

- 形态 A：右下角麦克风悬浮球（场景一 T0–T7）
- 形态 B：页内对话行（AI 自动语音 / AI 提示 / 系统语音 / 用户语音 / 系统回复，场景二 16 张图）

| 做 | 不做 |
|---|---|
| 对话行状态机（谁说、说什么、什么时候冒出来） | 不做语音识别算法本身（调 provider） |
| ASR / TTS provider 抽象（在线/离线可换，"是否需要离线识别"是 §10.4 待确认项） | 不计算业务结论（结论来自 `decision-engine` / `target-intel`） |
| 意图路由：把"推荐一个任务模式""哪个目标优先级最高""链路是否支持多集群协同"映射到模块能力调用 | 不推进阶段（交 `scenario-orchestrator`） |
| 播报脚本：阶段进入时的自动播报（如 T2-2 的链路自组网播报） | 不画 UI（宿主壳渲染对话行） |
| LLM provider 抽象（可选接入；未接入时回落模板话术） | — |

**关键设计点**：**LLM 是可选增强，不是依赖。**
本模块必须能在"没有大模型"的情况下用模板话术跑通全流程，否则演示环境一变就全瘫。

---

### 3.9 `alert-center` · 告警与事件

**定位**：回答"现在有没有需要人看的事"。

左导航有固定【告警】入口，界面图里也出现了"异常电磁信号聚集""目标区域出现移动迹象""残余威胁标记"等提示，
但没有任何模块承接。能力：告警产生（规则）、分级、去重合并、确认/消音、事件流订阅、审计留痕。
**不做**：推送（`realtime-hub`）、消息 UI（宿主壳）、业务判断（告警规则来自 `mission-baseline`）。

---

### 3.10 `report-service` · 报告

**定位**：回答"'导出任务报告'点下去产生什么"。

需求初稿里报告字段是明确的：报告编号（`MT-20250602-1532`）、生成时间、目标摧毁数量、覆盖区域、
集群协同效率、局部组网持续时长、成功率、资源消耗、任务存活率。
另有 §10.9 待确认项：格式（PDF/Word/在线）、保存位置、是否对接资料库。

**做**：模板 + 字段装配 + 渲染器抽象（HTML/PDF/DOCX 可换）+ 落库与下载。
**不做**：数据计算（向 `scenario-orchestrator`/`target-intel`/`resource-registry` 取只读快照）。

---

### 3.11 `mission-baseline` · 场景与基线

**定位**：回答"这套演示/这套预案的参数是多少"。

这不是"配置文件"那么简单。需求里的许多数字是**口径**而不是配置：132 架（48/32/28/24）、
6 个集群的四型配比、区域命名（A/B/C、核心搜索区）、失联判定倍数、评分权重、告警阈值、标绘模板。

**做**：场景/资源/集群/区域/阈值/评分权重/标绘模板的声明与校验、版本化、导入导出。
**不做**：业务计算。**关键**：所有模块的"魔法数字"必须来自这里，不允许散落在代码里。

---

## 5. L2 基础设施模块

### 4.1 `geo-data` · 地理数据服务

需求初稿 §10.5 待确认："二维底图/影像数据来源（自研、第三方、离线/在线）"。
`map-2d` 明确**不做瓦片工程**（切图、抓取、打包、分发），且要求"底图数据一律本地化，地址由宿主配置"。

所以缺一个：瓦片/影像的**获取 → 切片 → 清单 → 本地服务**（含缺块校验、版本、坐标系处理）。
现有 `map-2d/tiles/` 与 `map-2d/scripts/gen-tile-manifest.mjs` 已经给了消费侧的一半契约，本模块补生产侧。

### 4.2 `biz-store` · 业务库

`telemetry-store` 只认"带时间戳的流式数据"，**明确不做业务查询**（"哪个任务完成了"不在它范围内）。
而需求里有大量结构化实体：任务、目标、方案、告警、报告、操作日志、用户配置。

**关键边界**：`biz-store` 与 `telemetry-store` 不是一回事 ——
前者存"实体与关系"，后者存"时序流"。混在一起会让两边的查询都变慢且语义混乱。

### 4.3 `selfcheck` · 自检与健康

来源是启动阶段两张图 + 底部全局状态条，字段是逐字可抄的：

- 模块加载进度五项：地图引擎 / 通信链路 / AI 引擎 / 集群管理 / 数据服务（各带百分比）
- 分项自检五项：通信链路检测（卫星/数传/组网）、定位系统检测（GPS/北斗）、
  集群节点检测（节点状态/设备在线率）、后方指控检测（指控平台/数据交互）、系统安全检测（完整性/防护）
- 全局状态：网络连接、数据链路、GPS 定位、系统安全、系统就绪度

**做**：把各模块的健康探针聚合成一张自检表 + 进度上报接口。
**不做**：实际的检测实现（由各模块提供探针，本模块只编排与汇总）。
**注意**：`/health` 与 `/stats` 在 MAH 里已经有了，本模块是它们的**业务化升级**，不是重写。

### 4.4 `auth-access` · 权限

需求初稿 §10.1 待确认："面向的具体用户角色是什么？不同角色权限是否不同？"
现状：`assembly-host` 非目标里明确"权限/鉴权/TLS：全项目尚未开始"。

**做**：用户/角色/权限模型、按钮可见性、操作留痕。
**建议**：先只做"角色 → 可见能力"的声明，鉴权与 TLS 单独排期，别混进来。

### 4.5 `media-player` · 载荷视频与图像流

来源是 `TR-VID-01~04`：T3-2「六路集群图像流」、T6-1「多源融合图层：光电图像/雷达回波/电子频谱」、
T6-2「实时回传画面三路」、T2-2/场景三的「光电侦察画面 +【实时】标识 + 倍率 + 放大」。

**做**：通道清单与选择、播放控制（进度/音量/全屏）、多路同屏的布局与节流、画面元数据叠加
（倍率、锁定十字框、时间戳、"实时"标识）。
**不做**：流协议接入本身（RTSP 等属 `TR-VID-04`，当前无需求，只留扩展点）；不做地图联动（`situation-layer`）。

> 为什么单列：视频是三处界面的主体内容，把它塞进宿主壳会让"多路同屏 + 节流"这类有性能风险的部分无法独立测试。

---

## 6. L1 宿主：最后做，且只有两件事

### 6.1 宿主该收什么

| 收 | 说明 |
|---|---|
| 装配 | `add_subdirectory` / 别名引入、模块启动顺序、依赖注入 |
| 适配 | 反向接口实现：`ISink`、`ITransport`、`IStorageBackend`、`ILogSink`、`IDeviceSource` |
| 生命周期 | 启动序列（对应加载进度）、退出序列（`flush()` 后再 `stop()`） |
| 传输出入口 | WS/HTTP 路由、REST 挂载（模块只给路由处理器，不依赖 Web 框架） |
| 界面壳 | 顶部状态栏、左侧导航、底部状态条、右侧面板、对话行 —— **只做布局与绑定，不做判断** |

### 6.2 宿主不该收什么（红线）

| 不收 | 一旦收了会怎样 |
|---|---|
| 阶段推进条件 | 业务规则藏进 UI，无法单测、无法换壳 |
| 编组/评分/评级算法 | 与 `decision-engine` 双份实现，口径必然漂移 |
| 链路颜色语义 | 主题切换要改两处 |
| 显示模式 → 图层的映射 | 新增一个模式要动宿主，`situation-layer` 形同虚设 |
| 目标编号规则 | 又回到初稿 §10.12 的不一致 |
| 报告字段拼装 | 报告口径散在 UI 字符串里 |

> 判据可以机检：**宿主源码里出现 `if (phase === 'T5')` 这种判断，就是模块缺口的证据。**

> 图中 `sim-source` 与 `device-ingest` 是**互为替代**的两条上游：接实装时用前者，演示时用后者，

**三条硬约束（建议写进项目纪律）**

2. **业务模块之间不互相 import。** 组合发生在 `situation-layer` 与宿主两个地方 —— 这两个地方是**装配点**，不是逻辑点。
3. **`telemetry-store` 与 `biz-store` 不互相替代。** 时序流和业务实体分开走。

## 8. 实施顺序（按"每个模块都能独立自证"排）

| 阶段 | 模块 | 出口条件（可机检） |
|---|---|---|
| **S1** | `mission-baseline` + `scenario-orchestrator` | 给定基线，能跑完 T0→T7 状态机并输出阶段时间轴；无 UI 参与 |
| **S2** | `sim-source` + `resource-registry` | 仿真事件逐字段等于 `device-ingest` 归一化契约；132 架资源按方案分配到 6 集群，可用数恒等式成立 |
| **S3** | `link-topology` + `target-intel` + `decision-engine` | 两种拓扑（自组网/云边端）可产出图元结构且状态判定有迟滞；5 个目标台账跨阶段一致；三套方案评分可复现（同输入同输出，含"93% 从哪来"） |
| **S4** | `situation-layer` | 10 种显示模式逐一产出 `MapData`，在 `map-2d` 独立宿主内可见 |
| **S5** | `voice-interaction` + `alert-center` + `report-service` | 无 LLM 时模板话术跑通；告警规则可配；报告字段全部可溯源到模块 |
| **S6** | `geo-data` + `biz-store` + `media-player` + `selfcheck` + `auth-access` | 离线底图可用；重启后任务/目标/报告可查；三路视频同屏不掉帧；自检五项可返回 |
| **S7** | **宿主** | 装配 + 适配 + 界面壳；机检"宿主无业务判断"（DISC-04） |

> 为什么 S1 是 `mission-baseline`：**没有基线，后面每个模块都会自己编一套数字**，
> 这正是初稿 §10.12 那类不一致的根因。
>
> 为什么 `sim-source` 排在 S2 而不是最后：S3 起（链路质量、目标轨迹、方案评分）
> 都需要连续、有语义的数据流才能自证；靠人手发包验不了这些模块。
>
> **与既有 `TR-*` 阶段划分的关系**：技术需求文档 §7.1 已有 P0–P4 五个阶段与门规则。
> 本文的 S1–S7 是**模块建设顺序**，两者不冲突 —— 建议把它当作 P2（任务域）/P3（智能域）内部的施工顺序，
> 并在每个 `TR-*` 条目上标注"由哪个模块承担"，否则 `TR-BIZ-01~12` 会继续以"前端 store"形态存在，无法独立验收。

## 10. 下一步建议

1. 先评审本文 §0.2 的 18 个模块清单，**砍掉不认可的、补上漏掉的**（本文是讨论稿，不是冻结稿）。
2. 按 **§3.0 复用性总表**把模块分成两类，**分别订验收标准**（这是最容易扯皮的地方）：

   | 类别 | 模块 | 验收标准走哪套 | 交付形态 |
   |---|---|---|---|
   | **可复用（T1/T2/T3）** | `device-ingest` / `realtime-hub` / `telemetry-store` / `map-2d` / `geo-data` / `media-player` / `sim-source`(内核) / `biz-store`(机制) / `alert-center` / `report-service` / `selfcheck` | **走既有"交付验收清单"九条**（独立构建/运行/测试、接口稳定、反向接口、零业务依赖、零跨仓 import、有配套工具、能一句话说清）+ 本文 §1.3 的机检 | 独立仓 |
   | **业务（T4）** | `scenario-orchestrator` / `resource-registry` / `decision-engine` / `link-topology` / `target-intel` / `situation-layer` / `mission-baseline` / `voice-interaction`(意图) / `biz-store`(实体) | **不套"零业务词"**（它本来就是业务），改套：可单测 / 输入输出可复现 / 不依赖界面 | 留主仓 |

   > 混用标准是必然扯皮的根源：拿"零业务词"去卡 `decision-engine` 卡不动，
   > 拿"能一句话说清"去卡 `mission-baseline` 也说不清（它本质就是一套配置）。
3. 需要对外交付的模块，**先做拆分再开工**：`sim-source`（运动学内核 / 场景脚本）、`biz-store`（存储机制 / 实体定义）、
   `voice-interaction`（provider 抽象 / 意图与话术）—— 这三处一旦先写成一体，后面再拆要动已验收的代码。
4. 按 §8 的 S1 起步：`mission-baseline` + `scenario-orchestrator`，两者都不碰界面，可先写需求专篇。
5. 每个模块沿用现有四件套的文档三件套：`需求专篇（REQ-* 编号 + 验收标准）` → `契约（接口长什么样）` → `设计（怎么拆）`。
   已按此格式出稿两份（本轮新增）：
   - [`geo-data需求专篇.md`](./geo-data需求专篇.md) —— 31 条（`GEO-SRC/PKG/MNF/SRV/RTM/NFR`）
   - [`media-player需求专篇.md`](./media-player需求专篇.md) —— 28 条（`MDP-CHN/PLY/MUL/OVL/DGR/NFR`）
6. 宿主（assembly-host 升级 / mapApp 主仓）**最后做**，且先立 DISC-04 这条红线。
