# phase-engine · 阶段状态机引擎需求专篇

- 版本：v0.1（立项稿）
- 定位：把**"任务处于哪个阶段、能不能进下一阶段、怎么退"**抽为一个**独立可复用引擎**，供建仓、实现与验收直接使用
- 需求编号体系：`PHE-<域>-<序号>`；域见 §3
- 口径：**只有两种状态：✅ 已完成 ｜ ⏳ 待完成**（本专篇为立项文档，全部 ⏳）
- 分级用词：**MUST（必须，验收必查）/ SHOULD（应该，偏离需在决策记录说明）/ MAY（可选）**
- **部署形态：后端 C++ 仓**（与 `device-ingest` / `telemetry-store` 同构；不依赖 Web 框架，路由与持久化由宿主注入）
- 上游依据：
  - `docs/01-需求/智能任务管理系统_界面需求初稿.md`（§2.3 核心流程 T0–T7、§5 任务主流程、§6/§8 各阶段逐屏、§10.8 异常分支）
  - `docs/02-技术需求/智能任务管理系统_技术需求文档.md`（§4.8 `TR-BIZ-01`/`02`/`11`；**注意：TRD 现写"前端实现"，本专篇按后端引擎口径，见 §5 D1**）
  - `docs/04-设计/概要设计文档.md`（§4 业务数据流）
  - `docs/05-开发/开发接口契约规格书.md`（§2 统一约定、§4 `mission.phase` / `mission.progress` 事件）
  - [`模块仓库清单.md`](./模块仓库清单.md)、[`模块划分与缺口分析.md`](./模块划分与缺口分析.md) §3.1

| `applyWs()` 的 `mission.phase` / `mission.progress` | `useStore.ts` L568–581 | 前端接受阶段推送 | — |

**关键差距（本专篇主要价值）**

> 现状是一个**进度标签**，不是状态机：`setPhase` 只做 `idx*100/7 + UPDATE`，
> **没有任何前置条件**，因此 `T0 → T6` 直接跳过去在今天的实现里是合法的。
> 要成为可复用引擎，必须把"阶段图 + 前置条件 + 分支"变成**引擎内的显式数据**（由规则注入），
> 并由引擎统一裁决——这是 `模块划分与缺口分析.md` §3.1 已经点明的关键设计点。

## 1. 定位与边界

### 1.1 定位

```
业务侧（宿主 / 其它引擎）
   │  advance(to, context) / rollback(to) / getState()
   ▼
┌──────────────────────────────────────────────────────────┐
│  phase-engine（C++，无 Web 框架、无 SQL）                  │
│  DEF 阶段定义 → FSM 状态机 → GATE 前置条件 → BR 分支        │
│                      │                                   │
│                      ├──► TL 时间轴（供进度条 / 报告）      │
│                      └──► 出口：IPhaseSink（宿主实现）       │
└──────────────────────┬───────────────────────────────────┘
                       │ 阶段变更事件 + 时间轴
                       ▼
        宿主：落库 + 广播（EventHub / realtime-hub）+ 前端展示
```

**一句话**：phase-engine 回答"**现在处于哪个阶段、这个阶段允不允许离开、离开需要什么条件**"。
它不回答"这个阶段界面上该显示什么"（那是 `view-composer`），也不回答"阶段数据存哪张表"（那是宿主）。

### 1.2 为什么必须是独立引擎

1. **它被几乎所有其它引擎依赖**：`resource-alloc` / `scoring` / `entity-ledger` / `topology` / `view-composer` 的接口都带"当前阶段"这个入参。它不定，其余引擎的接口定不下来（`模块仓库清单.md` §6）。
2. **它有两个消费者**：本项目与第二套指挥/演训系统的阶段定义不同，但**阶段机机制相同**。
3. **它是异常分支的唯一落点**：初稿 §10.8 的"无人机失联 / 链路中断 / 边缘节点故障 / 自检不通过"需要一个统一的地方裁决，不能散在界面 `onClick` 里。

### 1.3 范围边界

| 做 | 不做 |
|---|---|
| 阶段定义装载与校验 | 🚫 不含 **T0–T7 的具体名称、数量与顺序**（属规则包 `policies/*`） |
| 阶段图与允许的迁移（含跳转、回退、重入） | 🚫 不做渲染、不做面板、不做按钮 |
| 前置条件（Gate）求值与拒绝原因 | 🚫 不做持久化（表结构属宿主） |
| 分支规则（异常/条件迁移） | 🚫 不做广播（出口是注入的 `IPhaseSink`） |
| 阶段时间轴与进度计算口径 | 🚫 不判定业务数据本身（"资源够不够"由 `resource-alloc` 回答，引擎只消费结论） |
| 任务台账的**阶段相关字段**（id/名称/类型/区域/时间/状态） | 🚫 不做任务报告（`report-engine`）、不做告警（`alert-engine`） |
| 迁移的幂等与并发拒绝 | 🚫 不做权限（`auth-access`） |

### 1.4 硬约束

| 约束 | 取值 | 依据 |
|---|---|---|
| 事件名与负载 | `mission.phase` 负载含 `{missionId, phase, scenarioKey, prevPhase, progress, phaseTitle}`；另发 `mission.progress` | 契约 §4；`Api.cc` L502–512 **现有负载不得破坏** |
| 进度口径 | 现状 `progress = round(idx * 100 / 7)` | `Api.cc` L493；可配置化后须保持默认一致 |
| 时间戳 | epoch 毫秒 | 契约 §2 |
| 语言/构建 | **C++17 + CMake ≥ 3.20**，与 `device-ingest` / `telemetry-store` 一致 | 模块仓库清单 §5 待定项 5 已定 |
| 依赖 | 仅 `nlohmann/json`（内置单头回落）；**不依赖 Drogon** | 对齐 `device-ingest` 的 `WITH_HUB=OFF` 做法 |
| 无业务词污染 | 引擎源码内 **MUST NOT** 出现 `T0…T7`、`敏捷拒止布控`、`光电无人机` 等 | 本专篇 §2.2 判据 |

## 3. 功能需求条目

### 3.1 阶段定义（PHE-DEF）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| PHE-DEF-01 | **MUST** 阶段定义为**外部数据**（规则包注入），引擎 MUST NOT 内建任何阶段名与数量 | 换一份阶段定义即换流程；全仓检索 `T0`–`T7` 零命中 | ⏳ |
| PHE-DEF-02 | **MUST** 定义结构至少含 `{ key, 序号, 标题(可随场景), 允许的前驱, 允许的后继, 前置条件集, 是否终态 }`；装载时 MUST 校验（重复 key / 孤立节点 / 终态可达性） | 故意给出一份含重复 key 的定义，装载失败并给出可读原因 | ⏳ |
| PHE-DEF-03 | **MUST** 支持多场景差异化：同一 `key` 在不同场景可有不同标题与不同前置条件 | 两个场景同阶段标题不同可复现；引擎内无硬编码标题 | ⏳ |
| PHE-DEF-04 | **SHOULD** 支持阶段定义版本号与变更检测，便于宿主判断是否需要迁移已建任务 | 定义版本变化可查询；旧任务按旧版本可解释 | ⏳ |

### 3.2 阶段迁移（PHE-FSM）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| PHE-FSM-01 | **MUST** 迁移接口 `advance(to, context)`；返回值 MUST 区分 `ok / rejected(reason) / already-there`，MUST NOT 抛异常 | 三种结果各有可读返回；非法迁移不改变当前状态 | ⏳ |
| PHE-FSM-02 | **MUST** 拒绝非法迁移：只允许定义中声明的迁移；**现状"任意跳转"行为 MUST 被消除** | `T0 → T6` 被拒绝并给出原因；`T0 → T1` 通过 | ⏳ |
| PHE-FSM-03 | **MUST** 前置条件（Gate）求值：每条迁移可挂 0..N 个 Gate，逐个求值并**一次性返回全部未通过项**（不是遇到第一个就停） | 挂 3 个 Gate 且 2 个不通过时，返回值列出这 2 项及各自原因 | ⏳ |
| PHE-FSM-04 | **MUST** Gate 由宿主按需注册（回调或表达式），引擎 MUST NOT 内建任何业务 Gate | 不注册 Gate 时全部迁移按图放行；注册后可拦截 | ⏳ |
| PHE-FSM-05 | **MUST** 回退语义明确：回退 MUST 声明是否需要清理后续阶段产物（`reversible` 标记） | 回退后引擎状态正确；需要清理的阶段返回可读提示 | ⏳ |
| PHE-FSM-06 | **MUST** 迁移幂等与并发拒绝：重复请求同一目标 MUST 返回 `already-there`；并发两个不同目标 MUST 只有一个成功，另一个得到 `busy`/拒绝（对齐契约 `code=1002` 语义） | 并发提交两个迁移，仅一个生效且状态一致 | ⏳ |
| PHE-FSM-07 | **MUST** 重入保护：同一阶段可重复进入时由定义显式声明（`reentrant`），未声明 MUST 拒绝 | 未声明重入的阶段二次进入被拒绝 | ⏳ |

### 3.3 分支与异常（PHE-BR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| PHE-BR-01 | **MUST** 条件迁移：定义中可声明"条件满足时走 A、否则走 B"；条件为宿主注册的回调 | 两种条件各走一次，路径可复现 | ⏳ |
| PHE-BR-02 | **MUST** 异常分支统一落点：自检不通过、链路中断、目标丢失、节点故障 MUST 都能表达为一次受控迁移或一次"暂停" | 四类异常各写一条用例，均可表达且不破坏状态一致性 | ⏳ |
| PHE-BR-03 | **MUST** 暂停/恢复：支持"停在当前阶段等待条件"，恢复后继续；暂停 MUST 可被查询 | 暂停后迁移被拒绝（带可读原因）；恢复后可继续 | ⏳ |
| PHE-BR-04 | **SHOULD** 终止语义：支持提前结束任务（非正常走完 T7），并标记终止原因 | 提前终止可查询、可区分于正常完成 | ⏳ |

### 3.4 任务台账（PHE-LEDGER）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| PHE-LEDGER-01 | **MUST** 任务实体：至少 `{ id, 名称, 类型, 场景键, 区域, 起始时间, 当前阶段, 状态, 进度 }`，由宿主注入持久化 | 建任务→查任务字段完整；重启后可恢复 | ⏳ |
| PHE-LEDGER-02 | **MUST** 任务状态与阶段解耦：状态（`created/running/paused/finished/aborted`）由引擎维护，阶段由定义决定 | 两套取值互不污染 | ⏳ |
| PHE-LEDGER-03 | **SHOULD** 任务列表与历史：可枚举任务、按状态与时间筛选（供 T7 与"返回场景选择"复用） | 多任务并存时列表正确 | ⏳ |
| PHE-LEDGER-04 | **SHOULD** 重置：可把任务重置到初始阶段，MUST 记录重置原因与操作者 | 重置后可查询到原因与时间 | ⏳ |

### 3.5 时间轴与进度（PHE-TL）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| PHE-TL-01 | **MUST** 阶段时间轴：输出 `[{phase, 标题, 进入时刻, 离开时刻?, 状态}]`，供进度条直接渲染 | 走完 4 个阶段后时间轴有 4 条且时序正确 | ⏳ |
| PHE-TL-02 | **MUST** 进度口径可配置：默认保持现状（序号线性 `idx*100/(n-1)`），但 MUST 支持按"各阶段权重"配置 | 默认值下与现状输出逐字节一致；换权重后按权重输出 | ⏳ |
| PHE-TL-03 | **MUST** 阶段耗时统计：每阶段驻留时长可查询（供 `report-engine` 的"任务用时""组网时长"） | 与外部时钟对比误差在可接受范围 | ⏳ |
| PHE-TL-04 | **SHOULD** 进度条节点标签：输出"任务下达 → 方案生成 → …"这类**展示用标签**，标签文本由规则注入 | 换规则即换标签；引擎内无硬编码文案 | ⏳ |

### 3.6 非功能性（PHE-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| PHE-NFR-01 | **MUST** 无副作用纯逻辑：给定相同（定义 + 迁移序列 + 时钟），结果 MUST 完全可复现 | 同一序列跑两次输出一致 | ⏳ |
| PHE-NFR-02 | **MUST** 零外部依赖：不依赖 Web 框架、不依赖 SQL、不依赖其它引擎内部 | 空环境独立构建；`grep` 跨仓 import 零命中 | ⏳ |
| PHE-NFR-03 | **MUST** 时间可注入：`IClock` 反向接口，使时序测试完全可复现 | 注入假时钟测试通过 | ⏳ |
| PHE-NFR-04 | **MUST** 独立交付：独立构建、独立示例、独立测试、独立验收脚本（退出码 0/1） | 空环境 clone → 一条命令构建 → 一条命令验收 | ⏳ |
| PHE-NFR-05 | **MUST** 出口为反向接口：`IPhaseSink`（阶段变更通知）由宿主实现，用于落库与广播 | 引擎内无直接落库与广播代码 | ⏳ |
| PHE-NFR-06 | **SHOULD** 性能：单次 `advance`（含 10 个 Gate）≤ 1 ms | 实测达标 | ⏳ |

## 4. 引擎与规则的划分（policies）

| 属引擎（可复用） | 属规则（`policies/mapapp`，项目专属） |
|---|---|
| 阶段图、迁移裁决、Gate 求值、分支、暂停/恢复、时间轴、进度口径 | **T0–T7 的 8 个 key、顺序、标题文案** |
| 任务状态机（created/running/…） | **各场景的阶段标题差异**（"通信链路建立" vs "云边通信与协同链路建立"） |
| 幂等、并发拒绝、重入保护 | **各阶段的前置条件内容**（如"T5 需已有推荐方案"） |
| 进度计算算法 | **各阶段权重**、进度条节点标签文案 |
| 事件负载结构 | **场景键与阶段标题的映射表** |

**判据**：引擎公开接口里出现 `T5`、`敏捷拒止布控`、`光电无人机` 即破线。

| R4 | 进度权重改口径导致与前端进度条不一致 | 界面回退 | D4 默认不变；改口径必须同步改验收基线 |
| R5 | TRD `TR-BIZ-01` 与 D1 冲突未修订 | 文档自相矛盾，实现者按旧的做 | 立项时同步改 TRD 该条 |
