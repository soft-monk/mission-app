# resource-alloc · 资源编组引擎需求专篇

- 版本：v0.1（立项稿）
- 定位：把**"手里有哪些资源、分给谁了、还能不能再分、编组合不合理"**抽为一个**独立可复用引擎**，供建仓、实现与验收直接使用
- 需求编号体系：`RAL-<域>-<序号>`；域见 §3
- 口径：**只有两种状态：✅ 已完成 ｜ ⏳ 待完成**（本专篇为立项文档，全部 ⏳）
- 分级用词：**MUST（必须，验收必查）/ SHOULD（应该，偏离需在决策记录说明）/ MAY（可选）**
- **部署形态：后端 C++ 仓**（与 `device-ingest` / `telemetry-store` 同构；不依赖 Web 框架，持久化由宿主注入）
- 上游依据：

  - `docs/02-技术需求/智能任务管理系统_技术需求文档.md`（§4.8 `TR-BIZ-03`；§4.10 `TR-UI`）
  - `docs/05-开发/开发接口契约规格书.md`（§3.3 资源与编组接口、§7.5 演示数据口径）
  - [`模块仓库清单.md`](./模块仓库清单.md)、[`模块划分与缺口分析.md`](./模块划分与缺口分析.md) §3.3

## 0. 完成情况总览

> 一句话：**共 31 条需求，全部 ⏳**（本专篇为立项，尚未开工）。
> **本引擎不是从零建**：后端已有台账与合计口径，缺的是分配算法与约束校验。

**现有资产映射**

| 现有实现 | 位置 | 已有 | 缺什么 |
|---|---|---|---|
| `uavs()` | `backend/src/api/Api.cc` L531–559 | 读 `uav_resource` 表；算 `totals`/`available`/`allocated`/`pending`；算 `allocatedTotal`/`totalAll`/`pendingTotal`/`onlineRate` | **只读表求合计，没有任何分配算法**；无超分校验；无约束 |
| `groups()` | `Api.cc` L561–565 | 读集群列表 | 无组成校验 |
| `generateGroups()` | `Api.cc` L566–576 | 生成集群 | 生成规则内容未定 |
| 基线数值 | `backend/src/core/Seed.cc` L3–5、L58、L208 | 场景一 光电48/雷达32/电子28/通信24、编组 124/132；场景二 22/12/10/8 | **这些是规则（policies）**，不该在引擎里 |
| 集群配比表 | 初稿 §8 T1-2 | 场景二 6 集群的四型配比（6/3/2/1 等） | 规则；且需可校验 |
| 前端资源展示 | `frontend/src/stores/useStore.ts` `refreshResources()` | REST 响应缓存 | 无逻辑 |

**关键差距**

> 今天的 `uavs()` **只做 SELECT + 求和**：把 `uav_resource` 表里的数字加起来返回。
> 因此"124/132"是**种子里写死的**，不是算出来的；"超分"在今天的实现里**不可能被发现**。
> 要成为引擎，必须把"可用数恒等式 + 分配合法性 + 利用率口径"变成引擎内的**显式约束**。

## 1. 定位与边界

### 1.1 定位

```
宿主 / 其它引擎（scoring 提供方案，policies 提供型号与配比规则）
   │  assign(plan) / release(clusterId) / utilization()
   ▼
┌──────────────────────────────────────────────────────────┐
│  resource-alloc（C++，无 Web 框架、无 SQL）                │
│  RSR 台账 → ALLOC 分配 → CONS 约束校验 → STAT 统计          │
│                      │                                   │
│                      └──► 出口：IResourceSink（宿主实现）    │
└──────────────────────┬───────────────────────────────────┘
                       │ 台账快照 + 变更事件
                       ▼
        宿主：落库 + 广播 resource.uav.state
```

**一句话**：resource-alloc 回答"**四型资源够不够、这次编组是否合法、用掉了多少**"。
它不回答"哪套方案更好"（`scoring`），也不回答"这些无人机现在飞到哪了"（遥测属 `device-ingest` + 台账汇入）。

### 1.2 为什么必须是独立引擎

1. **它有一组硬恒等式**（`available + allocated = total`、`pending = total - allocated`），是**可机检的一致性问题**，散在 SQL 里没人守得住。
2. **它被 `scoring` 依赖**：评分要用"资源利用率""可用数"作为输入。
3. **它有两个消费者**：换一套指挥系统，资源型号与配比规则会变，但**台账 + 约束机制相同**。

### 1.3 范围边界

| 做 | 不做 |
|---|---|
| 资源台账（多型号、可扩展，**不内建四型**） | 🚫 不含"光电/雷达/电子/通信"这些**型号名**（属规则） |
| 分配/释放/重新编组 | 🚫 不生成编组方案（`scoring` 生成，本引擎只校验与执行） |
| 约束校验（不超可用、型号匹配、下限保护） | 🚫 不做实时位置/电量（由遥测汇入接口喂入） |
| 统计与恒等式（利用率、就绪率、在线率口径） | 🚫 不做链路质量（`topology`） |
| 集群组成（成员、配比、任务方向/覆盖区域的**存储**） | 🚫 不做集群在地图上的画法（`view-composer`） |
| 遥测汇入：把归一化事件并入台账 | 🚫 不订阅网络（宿主喂入） |

### 1.4 硬约束

| 约束 | 取值 | 依据 |
|---|---|---|
| 现有接口形状 | `uavs()` 返回 `{items, totals, available, allocated, pending, allocatedTotal, totalAll, pendingTotal, onlineRate}` **不得破坏** | `Api.cc` L534–558；契约 §3.3 |
| 事件名 | `resource.uav.state`（前端 `applyWs` 已消费，触发 `refreshResources`） | `useStore.ts` L586–589 |
| 演示口径 | 场景一 48/32/28/24 总 132、编组 124；场景二 22/12/10/8 | 契约 §7.5；初稿 §6/§8 |
| 归一化事件字段 | 汇入形状 MUST 等于 `device-ingest` 归一化契约 `{deviceId, deviceType, kind, lng, lat, alt, heading, speed, battery, seq, ts}` | `device-ingest` README §关键约定 |
| 语言/构建 | C++17 + CMake ≥ 3.20；仅 `nlohmann/json` | 对齐既有 C++ 模块 |

## 3. 功能需求条目

### 3.1 资源台账（RAL-RSR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| RAL-RSR-01 | **MUST** 型号由宿主声明（`{ key, 名称, 能力标签[], 单位 }`），引擎 MUST NOT 内建任何型号 | 换一份型号声明即换资源类型；全仓检索 `光电`/`雷达` 零命中 | ⏳ |
| RAL-RSR-02 | **MUST** 台账字段：每型号 `{ total, available, allocated, pending }`；引擎 MUST 维护恒等式 `available + allocated = total` 与 `pending = total - allocated` | 任意操作序列后恒等式恒成立；人为破坏时校验报错 | ⏳ |
| RAL-RSR-03 | **MUST** 按任务维度隔离：不同任务各自一套台账，互不影响 | 两个任务并行时资源不串台 | ⏳ |
| RAL-RSR-04 | **MUST** 台账初始化来源可注入（基线数据由规则包提供） | 不提供基线时台账为空且可读；提供后按基线装载 | ⏳ |
| RAL-RSR-05 | **SHOULD** 型号可增删：运行中可追加新型号（数量为 0）并参与分配 | 追加后出现在清单与统计中 | ⏳ |

### 3.2 分配与释放（RAL-ALLOC）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| RAL-ALLOC-01 | **MUST** 分配接口 `assign(clusterId, allocation)`：按型号给量；MUST 先校验后生效（全成功或全不生效，不留半成品） | 一次分配中有一型超量 → 整次拒绝，台账不变 | ⏳ |
| RAL-ALLOC-02 | **MUST** 超分拒绝并给出可读原因：指出**哪个型号差多少** | 请求比可用数多 3 架 → 返回"型号X 需 14、可用 11" | ⏳ |
| RAL-ALLOC-03 | **MUST** 释放接口 `release(clusterId)`：回收该集群全部分配量，恒等式同步恢复 | 分配后释放，台账回到分配前状态 | ⏳ |
| RAL-ALLOC-04 | **MUST** 重新编组：以一套新方案整体替换现分配（先校验新方案，再原子替换） | 新方案不合法时**保持原分配不变** | ⏳ |
| RAL-ALLOC-05 | **MUST** 幂等：重复分配同一集群同一组成 → 返回 `already-applied` 且台账不变 | 重复调用后数字不变 | ⏳ |
| RAL-ALLOC-06 | **MUST** 未知型号/未知集群 MUST 被拒绝并可读 | 传不存在的型号 key → 明确拒绝 | ⏳ |

### 3.3 约束校验（RAL-CONS）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| RAL-CONS-01 | **MUST** 约束可注册：宿主可挂任意条约束（如"每集群至少 1 架通信型""单型占比不超 X%"），引擎 MUST NOT 内建业务约束 | 不注册约束时全部放行；注册后按约束拦截 | ⏳ |
| RAL-CONS-02 | **MUST** 一次性返回**全部**违反项（不是遇到第一个就停） | 同时违反 3 条约束 → 返回值列出 3 条 | ⏳ |
| RAL-CONS-03 | **MUST** 配比校验：可校验"某集群四型配比是否为声明的比例/数量" | 场景二 6 集群配比表逐行校验通过；改错一行被拒 | ⏳ |
| RAL-CONS-04 | **MUST** 下限保护：分配后可用数为负 MUST 不可能出现（由 ALLOC-02 兜底，CONS 层再审一次） | 任意操作后可用数 ≥ 0 | ⏳ |
| RAL-CONS-05 | **SHOULD** 完整性校验接口：对当前全部分配做一次体检（恒等式 + 约束 + 覆盖率），输出可读报告 | 故意破坏一处 → 报告定位到具体集群与型号 | ⏳ |

### 3.4 统计与利用率（RAL-STAT）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| RAL-STAT-01 | **MUST** 统计输出保持现有字段形状：`{items, totals, available, allocated, pending, allocatedTotal, totalAll, pendingTotal, onlineRate}` | 与现状接口返回逐字段可比对 | ⏳ |
| RAL-STAT-02 | **MUST** 利用率口径显式且可配：默认 `利用率 = 已分配 / 总数`（现状 124/132 = 93.9% 的展示口径需与界面一致） | 同一台账下引擎与界面显示一致；换口径可配置 | ⏳ |
| RAL-STAT-03 | **MUST** 就绪率与在线率区分口径：`readyRate`（分配且在线）/`onlineRate`（在线/总数）各自定义并分别可查 | 两个指标独立变化可复现 | ⏳ |
| RAL-STAT-04 | **SHOULD** 按集群维度统计：每集群占用、就绪百分比（供 T1-2 左侧"方案资源总览"） | 6 集群各自数字正确且合计等于总量 | ⏳ |

### 3.5 遥测汇入（RAL-ING）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| RAL-ING-01 | **MUST** 汇入接口 `applyTelemetry(normalizedEvent)`：入参形状**逐字段等于** `device-ingest` 归一化对象，引擎只更新台账（在线、电量、位置引用） | 用 `device-ingest` 的真实事件驱动，台账正确更新 | ⏳ |
| RAL-ING-02 | **MUST** 不订阅网络：引擎 MUST NOT 自行收包或连 WS；由宿主喂入 | 引擎内无网络代码 | ⏳ |
| RAL-ING-03 | **MUST** 型号映射由规则提供：把 `deviceType` 映射到型号 key，引擎 MUST NOT 内置映射 | 换映射即换归属；引擎内无 `uav`/`optical` 字面量 | ⏳ |
| RAL-ING-04 | **SHOULD** 离线判定口径可配（默认继承"3× 上报周期"） | 停发后按时标为离线；恢复后回到在线 | ⏳ |
| RAL-ING-05 | **SHOULD** 高频汇入降载：台账更新 MUST NOT 触发逐事件广播（合并后按节拍通知） | 1000 台 × 1 Hz 下通知次数显著低于事件数 | ⏳ |

### 3.6 非功能性（RAL-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| RAL-NFR-01 | **MUST** 无副作用可复现：给定相同（基线 + 操作序列），输出 MUST 完全一致 | 同序列跑两次结果一致 | ⏳ |
| RAL-NFR-02 | **MUST** 零外部依赖：无 Web 框架、无 SQL（持久化走注入的 `IResourceStore`）、不依赖其它引擎内部 | 空环境独立构建；跨仓 import 零命中 | ⏳ |
| RAL-NFR-03 | **MUST** 线程安全：分配与释放可被多线程调用而不破坏恒等式 | 并发压测后恒等式仍成立、无丢更新 | ⏳ |
| RAL-NFR-04 | **MUST** 出口为反向接口：`IResourceSink`（台账变更）由宿主实现用于落库与广播 | 引擎内无直接落库与广播 | ⏳ |
| RAL-NFR-05 | **MUST** 独立交付：独立构建、独立示例、独立测试、独立验收脚本（退出码 0/1） | 空环境 clone → 一条命令构建 → 一条命令验收 | ⏳ |
| RAL-NFR-06 | **SHOULD** 性能：1000 台规模下 `applyTelemetry` P95 ≤ 50 µs；`assign` ≤ 1 ms | 实测达标 | ⏳ |

## 4. 引擎与规则的划分（policies）

| 属引擎（可复用） | 属规则（`policies/mapapp`，项目专属） |
|---|---|
| 台账结构与恒等式 | **型号清单**：光电 / 雷达 / 电子 / 通信 及其能力标签 |
| 分配 / 释放 / 重新编组 / 幂等 / 超分拒绝 | **各场景的基线数量**：48/32/28/24（132）、22/12/10/8 |
| 约束注册与求值、一次性返回全部违反项 | **具体约束**：每集群最小架数、配比表（6/3/2/1 等） |
| 统计字段形状、利用率/就绪率/在线率的**计算** | **利用率口径的取值**（用哪个分子分母）、就绪率定义 |
| 遥测汇入与合并通知 | **`deviceType` → 型号 key 的映射**、离线判定倍数 |
| 线程安全、出口接口 | **集群名称与任务方向文案** |

**判据**：引擎公开接口里出现 `光电无人机`、`124/132`、`6/3/2/1` 即破线。

## 6. 风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 现状基线是**种子写死**的，改引擎后台账首末状态可能变化 | 演示数字与截图不符 | 用规则包精确复刻契约 §7.5 的数值，并加一条"与截图逐字一致"的验收 |
| R2 | 约束注册被写成业务逻辑容器 | 引擎再次被穿透 | 约束只接"是否满足 + 原因"，且 MUST 无副作用（测试锁定） |
| R3 | 1000 台高频汇入导致广播风暴 | 前端卡顿 | RAL-ING-05 合并通知；实测门槛纳入验收 |
| R4 | 与 `scoring` 的边界模糊（评分也要"利用率"） | 双份实现 | 利用率**只由本引擎算**，`scoring` 通过接口读取 |
| R5 | 型号抽象过度（做成通用资源池引擎） | 配置地狱 | 只支持"按型号计数 + 上下限约束"，不做单位换算、不做嵌套资源 |

## 7. 验收清单

- [ ] 空环境 clone → 一条命令构建 → 一条命令跑通验收脚本（退出码 0）
- [ ] 全仓检索型号名（光电/雷达/电子/通信）与基线数字 → 零命中
- [ ] 任意操作序列后恒等式 `available + allocated = total` 恒成立
- [ ] 一次分配中含超量型号 → 整次拒绝，台账不变，原因指出差额
- [ ] 分配后释放 → 台账逐字段回到分配前
- [ ] 用不合法新方案重新编组 → 原分配保持不变
- [ ] 重复分配同一集群同一组成 → `already-applied`，数字不变
- [ ] 同时违反 3 条约束 → 返回值列出全部 3 条
- [ ] 场景二 6 集群配比表逐行校验通过；改错一行被拒
- [ ] `uavs()` 字段形状与现状逐字段可比对
- [ ] 用 `device-ingest` 真实事件驱动汇入，台账正确更新
- [ ] 注入假时钟，同一操作序列跑两次结果完全一致
- [ ] 并发调分配/释放，恒等式仍成立
- [ ] 1000 台 × 1 Hz 汇入时通知次数显著低于事件数，P95 ≤ 50 µs
