## 0. 三十秒看懂

这是一个**被拆成 17 个独立 Git 仓**的无人集群任务指挥系统。每个仓是一个"拿走就能用"的模块；**模块之间互不 import**，靠宿主装配。

```
①入口            ②管道             ③留存              ④出口
device-ingest → realtime-hub   →  telemetry-store  →  map-2d      ← 这一条已通
────────────────────────────────────────────────────────────────
geo-data / media-player                                    ← 通用能力，已实现
phase-engine / topology / entity-ledger                     ← 业务引擎，已实现
resource-alloc / scoring / view-composer / alert-engine /
report-engine / selfcheck / llm-provider                    ← 待实现
mapApp（= smart-mission-system）主项目 + 最终宿主            ← 过渡原型，将来重写
```

### 1.2 网络：代理与直连**都会失效**，要会切换

> **实测教训（本会话踩过两次，方向相反）**：
>
> | 时段 | 直连 | 走代理 `127.0.0.1:7897` |
> |---|---|---|
> | 会话早期 | ❌ TLS handshake timeout | ✅ 可用 |
> | 会话后期（代理被关时） | ✅ **可用** | ❌ `SSL_ERROR_SYSCALL` |
>
> **代理端口在监听 ≠ 代理可用。** 一旦 `git push` 报 `SSL_ERROR_SYSCALL`，
> 先按下面三步定位，**不要反复重试**：

```powershell
# ① 直连测试（清空代理）
git -c http.proxy= -c https.proxy= ls-remote https://github.com/soft-monk/phase-engine.git HEAD

# ② 走代理测试
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 ls-remote https://github.com/soft-monk/phase-engine.git HEAD

# ③ 看系统代理开关（0 = 关）
Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' | Select-Object ProxyEnable, ProxyServer
```

**哪个通就用哪个**：

```powershell
# 走代理
git config --global http.proxy  http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897

# 或直连（清空代理配置）
git config --global --unset http.proxy
git config --global --unset https.proxy
```

> **DSH 侧的「环境开关」**（侧边栏底部，`dsh-proxy` 插件）控制的是**系统代理**，
> 它同时影响 `google_search` 等工具。**Agent 无法控制它**——需要时请人切换。
> 注意：`gh` 走的是自己的认证通道，**代理关掉后 `gh api` 仍可能通**，别用它来判断网络状态。

**基础配置**：

```powershell
git config --global user.name  softmonk
git config --global user.email "60962648+soft-monk@users.noreply.github.com"
gh auth login      # 确认 gh auth status 显示 soft-monk
```

> **坑**：PowerShell 里 `gh some-cmd --jq '复杂表达式'` 会**被引号规则拆坏**（报 `accepts 1 arg(s), received 3`）。
> 凡带 `--jq` 的 `gh` 调用，**写进 `.mjs` 用 `spawnSync` 跑**，不要直接写在 `pwsh` 命令里。

### 1.4 已知环境坑（都会咬人）

| # | 坑 | 现象 | 处置 |
|---|---|---|---|
| 1 | **`npm` 在 pwsh 里被拦** | `npm.ps1 cannot be loaded because running scripts is disabled` | 用 `npm.cmd`，或 `Set-ExecutionPolicy -Scope Process RemoteSigned` |
| 2 | **GitHub 直连不通** | `SSL_ERROR_SYSCALL` / TLS handshake timeout | 配 §1.2 的代理；**偶发推送失败就重试**（本会话遇过两次，重试即成功） |
| 3 | **`gh --jq` 引号被拆** | `accepts 1 arg(s), received 3` | 见 §1.2 末尾的坑 |
| 4 | **CRLF 警告刷屏** | `LF will be replaced by CRLF` | 无害，忽略 |
| 5 | **中文路径** | `docs/需求/xxx.md` 在 `git status` 里显示为八进制转义 | 无害；脚本里用 `Test-Path -LiteralPath` |
| 6 | **`Select-Object -First N` 接长跑进程** | 管道被截断 → 进程被杀（宿主退出码 -1/1），看起来像"命令崩了" | 长跑进程用 `run_in_background` + `job_output`，别用 `-First` 接 |
| 7 | **模块验收必须串行空载** | `resource-alloc` 的 assign P95 ≤ 1 ms 对负载敏感，并发跑两仓验收会假失败；ctest 一失败 `acceptance.ps1` 还会提前退出、打不出汇总 | 一次只跑一个仓的验收，别和其它重活并发 |
| 8 | **Node 全局 WebSocket 与 fetch 共用 dispatcher** | 脚本里先 `fetch` 再 `new WebSocket` → 升级请求被并到那条 keep-alive 连接上：只来一个 error、**永不 open** | 脚本里**先建 WS，再发 HTTP** |
| 9 | **hub 心跳判死窗（现 60 s）** | 只收不发的 WS 连接会被踢（**2026-09-20 前** 1.5 s x 3 = 4.5 s；**现为 15 s x 4 = 60 s**，见 `ma/hub_engine.cc`）；长过程采集"一条都收不全" | 采集器自己每 ~1.2 s 发 `sys.ping` 保活 |
| 10 | **headless 截图两坑** | `backdrop-filter` 在无 GPU 下整块面板不参与合成（截图"面板消失"）；新建 CDP target 默认视口可能只有 ~420 px 高 | 面板别用 `backdrop-filter`；脚本先 `Emulation.setDeviceMetricsOverride(1280x800)` |
| 11 | **React 样式简写 diff 陷阱** | 同一棵树位置切换元素时移除 `inset` 会**连带清掉 `top`**，而"值没变"的 `top` 不会被重设 → 整屏塌成 0 高、内容全在视口外 | 一律用 `left/right/bottom` 长写，**别把 `inset` 和 `top` 混用** |

### 3.2.2 两条并行验收的硬约束（踩过，务必遵守）

1. **同一台机器上两条宿主实例必须错开 UDP 接入端口**：都绑 `45500` 时 Windows 只把报文投给**先绑定**的
   那个 socket，后起的那条会 `packets=0 / nodesOnline=0/10` → 它的启动加载永远过不去
   （症状很像"仿真坏了"）。P7 自证用的是 `scripts/.p7-config.json`（仅把 ingest 改到 45501）。
2. **验收脚本不要并发跑**：它们都要驱动同一个宿主、会把流程推走（`p7-check` 里已内置互斥闸门，并发时后到的那条回 `1002`）。
3. **前端事件腿的心跳与宿主判死窗**：ws-client 默认 15 s 一次心跳，且 `sys.welcome.data.heartbeatMs` 会覆盖页面里的值。
   **2026-09-20 之前**：宿主为验收可观测把判死压到 1.5 s x 3 = 4.5 s，页面在后台被节流就会反复被踢
   （表现为切屏慢半拍、`/stats` 的 `clientCount` 恒 0、左下角反复弹"断线 X s 后已重连"）。
   **2026-09-20 起**：判死窗调回 **15 s x 4 = 60 s**（`ma/hub_engine.cc`），上述问题不再出现；
   `useFlow.ts` 的 `heartbeatMs: 1200` 保留为 welcome 到达前的保底值。**改判死窗时两处一起看。**

### 4.5 用 DSH 跑并行开发：**别重蹈我的覆辙**

**教训（本会话真实踩过）**：

> 我用 `workflow` 工具前台阻塞地跑"3 模块 × 4 阶段 = 12 个 agent"，结果**界面长时间无反馈**，
> 用户以为卡死。而实际上 agent 的产出**早已落盘**，只是被编排的**阶段屏障**挡住看不到。

**做法**：

| 场景 | 用什么 |
|---|---|
| 3 个模块并行实现 | **后台 `subagent` ×3**（立刻返回 id，完成时通知） |
| 单模块四阶段串行 | 一个后台 subagent 内部自己走完，**不要**用 `workflow` 的阶段屏障 |
| 需要几十个 agent 扇出 | `workflow` + `pipeline()`（**stage 之间无屏障**），且**放后台** |
| 跨轮长任务 | `create_goal` |

**其它实操要点**：

- **一个 agent 包一个模块**，prompt 里写明：读哪些文档、硬性要求、验收判据、**不许 commit/push**（宿主统一提交）
- **宿主统一提交**：agent 只写文件，宿主跑实测 → 清调试残渣 → commit → push。这样 agent 不会互相踩 git
- **agent 会在工作区留垃圾**：实测留过 `build.txt`/`cfg.txt`/`err.txt`/`out.txt`/`selftest.txt`/`build_probe2/`，以及**5 个 Chrome profile 目录**（`media-player` 拉 headless Chrome 实测留下的）。提交前必查：`Get-ChildItem <repo> -File | Where-Object { $_.Name -match '\.(txt|log|bak)$' }`
- **agent 会挑出你的文档缺陷**：这是好事，认真核实后改文档，别改实现
