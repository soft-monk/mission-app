# P7 · 一键演示（Excel 11 步串联 + 倍速 + 可重跑）

> 出口条件（《业务层宿主层实施方案》§5 P7）：**一键从启动跑到总结，无人工干预**。
> 真机自证：`scripts/p7-check.mjs`（下面 §5 有命令）。

## 1. 起服务（本阶段固定 **8100**）

```powershell
cd D:\dsh_workpath\webMap\mission-app
cmake --build build --config Release          # 0 error 才算过
.\build\bin\Release\mission_host.exe --port 8100
# 就绪行：[host] engines ready: phase=1 resource=1 ... ；页面 http://127.0.0.1:8100/
```

* **不要用 8099**：那条口子上有另一条并行自证（前端），两边会互相打断。
* **接入端口也要错开**：`config.json` 的接入点固定 `45500`，而 Windows 对同一 UDP 端口只把报文
  投给**先绑定**的那个 socket —— 实测第二条实例 `packets=0 / receiving=false / nodesOnline=0/10`
  （启动加载的"链路/集群节点"探针就会过不去）。所以第二条实例用配置副本：
  `scripts/.p7-config.json`（`config.json` 的复制，**只改** `ingest.points[0].port=45501` + 相对路径
  改绝对路径，因为相对路径锚在配置文件旁边）；`config.json` 本身未被改动。
  `mission_host.exe --config scripts\.p7-config.json --port 8100`
* 同一份仓库第二个 build 目录（`build-p7`）只是想并行编译时的做法，产物一样：
  `cmake -S . -B build-p7 -G "Visual Studio 17 2022" -A x64 -DMA_VCPKG_DIR=<vcpkg_installed>`
  （原因：`build/bin/Release/mission_host.exe` 被别人的实例占用时无法重新链接）。
* `config.json` 的 `simAutoStart=true`：**数据链路开机就在跑**（设备 3 s 无报文就被判失联，
  而启动加载的"链路/集群节点"探针要求真实报文），所以"起飞/变速"是步 6 的控制语义。

## 2. 一键跑（无人工干预）

```powershell
# 一条命令跑完 11 步（含重置 + 倍速演示）
$body = '{"verb":"flow.runAll","params":{"speed":8}}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8100/api/command `
  -ContentType 'application/json' -Body $body | ConvertTo-Json -Depth 6
```

参数：`from?`(1..11) `to?`(1..11) `speed?`(1|8|60) `pacingMs?`(启动加载节拍，0=尽量快)
`stepPacingMs?`(步与步之间的停顿，默认 0 = 全速；演示时给 700 让界面看清每一屏 —— 只影响节奏，
不进 `steps[].ms`) `reset?`(默认 true) `planId?`(`from>4` 时给第 5/9 步用) `bootWaitMs?` `targetsWaitMs?`。

* **每一步都走 `POST /api/command` 的同一个入口**（与前端按钮、p2–p6 脚本完全同一条路），
  `flow.runAll` 里**没有**任何引擎调用 —— 不抄近路，也不另写一份"更快的实现"。
* 回执：`steps:[{step,key,verb,code,ms,calls[],detail}]` + `speedDemos[]` +
  `summary:{ok,failedStep,failedVerb,failedReason,totalMs,speed,stepsRun}` + `flow`(收口读数)。
* **失败即停**：某步 `code!=0` → `summary.ok=false`、`failedStep=N`、后面的步骤不跑；
  外层 `code` 就是那一步的码（1003/1004/1005…），负载在 `error` 里（协议 §3 的回执形状）。
* **互斥**：同一条流程上同时只允许一条串联（前端连点两次"一键"会撞上）→ 第二条回 **1002**
  （协议里 1002 唯一的用途），它不会动流程；等第一条跑完再发。
* `reset` 失败（例如 `sim.reset` 回 1005）→ **一步都不跑**：跑出来的是"接着上一轮"的假串联，
  所以准备阶段任一失败就直接如实回失败（`summary.prepareFailed`）。

## 3. 怎么变速

`speed` 在**第 6 步**经 `sim.speed` 生效，并在同一步演示一次变速（默认 `8× → 60× → 1×`），
每次紧跟一条 `sim.state`，读数原样进 `speedDemos[]`（`requested` / `observed` / `match` + 完整 `state`）；
演示完回到请求的倍速，后面几步（目标出现、打击、报告）按它跑。手动变速：

```powershell
'{"verb":"sim.speed","params":{"speed":60}}'   # 只接受 1 / 8 / 60（引擎取值域，别的回 1000）
'{"verb":"sim.state"}'                          # 读回 running/paused/speed/simElapsedMs/platforms/emitted
```

## 4. 失败怎么定位（每步 verb + code + 看哪里）

| 步 | verb（主 / 步内全部） | 非 0 码常见含义 | 去哪看 |
|---|---|---|---|
| 1 | `boot.run` | 1005 启动加载未在 `bootWaitMs` 内完成（真实条件未成立） | 宿主 stdout 的 `[flow] 启动加载：<key> 就绪=` 行；`/api/state` → `boot.modules[]`（含 `status/detail/metric`） |
| 2 | `selfcheck.run` | 1005 规则包未装载 | `/api/state` → `selfCheckReady/selfCheckNote`、`selfCheck.items[]`；`selfcheck.report` |
| 3 | `flow.enter` + `situation.snapshot` | 1003 缺 `name/scenarioKey` | `/api/state` → `missionId/phase/phaseFromEngine`；宿主日志 `[host] 规则包：…` |
| 4 | `mission.advance{to:"T1"}` → `alloc.plans` | 1003 未进任务 / 1004 没给出可用 `planId` | 该步 `calls[].readings.recommendedId/recommendedPercent/itemsCount`；`/api/state` → `plans` |
| 5 | `alloc.adopt` → `alloc.confirm` → `alloc.assign` | 1003 硬前置未满足（`unmet:["not-adopted"]`） | `calls[].readings.error.unmet`；`/api/state` → `plans.adopted/confirmed`、台账实体数 |
| 6 | `mission.advance{to:"T2"}` → `sim.speed`×N → `sim.state`×N → `topology.evaluate` → `sensor.status` | 1003 阶段 Gate 未过（`force` 的两次回执都在 `calls[]`） | `calls[].readings`（`step/phase/skippedGates`）；`/api/state` → `phase`；`sim.state` 事件 |
| 7 | `targets.list`（轮询）+ `targets.detail` + `media.channels` | 1004 等 `targetsWaitMs` 仍无目标（探测没落账） | `sensor.status`（挂接/覆盖）、`/api/state` → `sensor`、`targets.detection{registered,merged,noMission,failed,lastError}` |
| 8 | `strike.plans` → `strike.adopt` | 1004 没给出可用 `planId` | `calls[].readings.itemsCount`；`/api/state` → `strike.plans` |
| 9 | `strike.confirm`（1003 才补 `strike.adopt` 重试一次）→ `guidance.plan` | 1003 前置/阶段 | `calls[]` 两条 confirm 的回执；`/api/state` → `strike.adoptedPlanId/confirmedPlanId` |
| 10 | `exec.run` | 1003 动作/状态迁移被引擎拒；1005 俯冲未施加 | `calls[].readings.stateAfter/hit/diveApplied`、`error.unmet`；`/api/state` → `exec.records`、`report.last.dataGaps` |
| 11 | `report.generate` | 1005 report-engine/规则包问题 | `calls[].readings.reportNo/dataGaps`；`/api/state` → `report.available` |

> 阶段是**按 11 步的对应关系合法推进**的（步 4 = T1、步 6 = T2）——不是靠 `force` 跳过阶段图。
> 实测：从 T0 直接 `mission.advance{to:"T2"}`（非 force）phase-engine 回 **1000 且不带 message**，
> 所以串联里先在步 4 推进 T1，步 6 的 T2 就是合法迁移（步 6 仍保留"非 force 失败才 force 重试一次"）。

**演示时的已知红项（与本阶段无关，P2 起就这样）**：第 2 步自检的"通信链路检测"里**卫星链路**恒为
`abnormal`（"通信链路中断"）。原因是 `selfcheck/probes/mapapp/probe_pack.cc:166` 的 `satcomLink`
只有"ok / failed"两态，而宿主如实报 `satcomLinkUp=false`（本工程没有卫星链路）——
规则包那个 `unconfigured`（中性态）等级这条探针用不上（`gnss`/后方指控两条有 `*Configured` 键，
所以显示"未配置（中性态）"）。修法在模块侧（给该探针加 configured 分支），**不在本阶段范围**。
自检整体 `status=ok`、5 个模块卡全 ok，所以它不影响流程推进，只是屏幕上多一个红条。

**通用三步**：① 回执 `steps[i].calls[]`（每条命令的 `code/ms/readings/error`，含引擎原话）；
② `/api/state`（`step/phase/boot/selfCheck/sensor/simulation/strike/exec/report` 各自一段）；
③ 宿主 stdout（`[flow]` 前缀：启动加载逐模块、`sim.reset`、`flow.runAll 完成/失败` 汇总行）。

## 5. 重置与自证

```powershell
# 不重启进程回到真起点（仿真源**重建**：平台回装配期坐标、仿真时钟归零、探测出口重挂）
'{"verb":"sim.reset"}'      # 回执：reset=true, simElapsedMs=0, platforms=N, speed, attachments=N, before/after
'{"verb":"mission.reset"}'  # 清任务与阶段（下次 flow.enter 建新任务）
'{"verb":"boot.reset"}'     # 清启动进度与自检报告
node scripts/p7-check.mjs http://127.0.0.1:8100/     # 全绿 = P7 出口条件（P7_SKIP_REGRESS=1 可跳过 p2–p6 回归）
```

`flow.runAll` 的 `reset=true`（默认）会按 `sim.reset → mission.reset → boot.reset` 自己造这个起点
—— 这就是"**第二遍仍然全绿**"的前提：只清任务不重建仿真，跑出来的是接着上一轮的假串联。

`p7-check.mjs` 末尾会把 p2–p6 在同一 URL 上复跑一遍（子进程，串行）并打印汇总行。

**已知抖动（不在 P7 里，但会影响"回归全绿"的观感）**：`p2-check` 的最后一条断言是
"`flow.enter` 之后 **600 ms** 内页面切到步 3"。实测（`scripts/.p7-latprobe.mjs`，临时探针）：
`/api/state` 中位 21 ms（很快），但**页面换步延迟稳定在 670–760 ms** —— 因为**页面切屏走的是
`POLL_MS=500 ms` 的 `/api/state` 轮询兜底**，不是 WS 事件腿；而只收不发的 WS 连接会被 hub 判死踢掉
（实测：静默客户端 ~4.5 s 后 `heartbeatClosed++`，页面加载后 `/stats` 的 `realtime.clientCount` 恒为 0）。
→ 600 ms 的窗口刚好卡在实际延迟之下，这条断言约 1/3 概率失败（与本阶段改动无关：P7 没动
`apps/web` 与 hub）。所以 p7-check 对回归脚本**最多重试 2 次**，每次的汇总行与失败断言**都打印**
（不拿后一次盖掉前一次），日志在 `scripts/.p7-regress-*.log`。
**根治办法（前端侧一行）**：页面像验收脚本那样每 ~1.2 s 发一次 `sys.ping` 保活，事件腿就活了，
换屏延迟从 ~0.7 s 降到 <50 ms。
